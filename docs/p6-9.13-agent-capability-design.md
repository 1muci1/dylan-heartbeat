# P6-9.13 Agent Capability Layer Design

## 1. Agent 能力系统架构

### 1.1 目标

Agent Capability Layer 为 AI Companion Runtime 提供受控、可发现、可审计的外部能力调用框架，使 Agent 能在用户明确授权后请求设备或服务执行有限操作。

本层解决的是“Agent 可以申请使用哪些能力、在什么条件下可以执行、执行结果如何安全返回”，而不是赋予 Agent 对手机或系统的默认控制权。

核心原则：

- 能力必须显式注册，未注册能力默认拒绝。
- 每次调用必须经过 Permission Gate。
- 设备端最终执行仍受操作系统权限和用户授权控制。
- 高风险操作需要即时确认，不能仅依赖历史授权。
- 执行行为必须对用户可见，并留下最小化审计事实。
- 模型只能提出结构化能力请求，不能直接访问设备 API。
- Capability 执行结果不能直接修改 Memory、State、关系等级或 AI 人格。

### 1.2 建议分层

```text
Agent / Model
    |
    | 结构化 capability request
    v
Capability Request Validator
    |
    v
Tool Registry ---------> Capability metadata / schema / risk
    |
    v
Permission Gate -------> User grants / runtime policy / device state
    |
    v
Execution Dispatcher
    |
    +--> Local Device Bridge
    +--> Mobile Agent via VPS Relay
    +--> Server-side bounded tool
    |
    v
Result Sanitizer ------> structured result
    |
    v
EventStore ------------> minimal audit facts
```

### 1.3 核心组件

- `CapabilityRequestValidator`：验证 tool name、参数 schema、请求来源、幂等键和有效期。
- `ToolRegistry`：保存能力定义，不保存用户秘密或设备凭据。
- `PermissionGate`：根据风险、用户授权、设备权限、会话状态和调用范围决定允许、确认或拒绝。
- `ExecutionDispatcher`：将已授权请求路由到正确 Device Bridge 或服务器工具。
- `DeviceBridge`：封装平台能力，不向模型暴露原生系统接口。
- `ResultSanitizer`：按能力输出 schema 过滤结果。
- `CapabilityAudit`：通过 EventStore 记录最小化执行事实。

### 1.4 建议状态机

```text
requested
  -> validation_failed
  -> permission_required -> approved -> dispatched -> succeeded
                         |          |             -> failed
                         |          -> expired
                         -> denied
  -> rejected
```

状态转换必须由 Runtime 控制。模型不能将请求自行标记为 approved 或 succeeded。

## 2. Tool Registry

### 2.1 职责

Tool Registry 是所有 Agent 能力的唯一目录，负责：

- 工具名称与版本。
- 输入和输出 schema。
- 风险等级。
- 支持的平台和执行位置。
- 所需系统权限。
- 是否需要用户即时确认。
- 是否幂等、是否允许重试、最大执行时间。
- 输出敏感级别和日志过滤规则。

Registry 只描述能力，不执行工具，也不授予权限。

### 2.2 工具定义草案

```json
{
  "name": "device.reminder.create",
  "version": "1",
  "description": "Create one visible reminder after user authorization.",
  "inputSchema": {},
  "outputSchema": {},
  "risk": "write_low",
  "executionTarget": "mobile_device",
  "platforms": ["android", "ios"],
  "requiredPermissions": ["reminders"],
  "confirmation": "per_call",
  "idempotent": true,
  "timeoutMs": 15000,
  "retry": "never"
}
```

### 2.3 建议风险等级

- `read_public`：读取非敏感、用户可见的设备状态。
- `read_private`：读取联系人、日历、位置等受保护数据。
- `write_low`：创建提醒、草稿等可见且易撤销的内容。
- `write_high`：发送消息、发起通话、删除数据、付款或账户操作。
- `system_sensitive`：设备管理、辅助功能、后台持续控制等高权限能力。

默认规则：

- 未识别风险等级拒绝注册。
- `write_high` 必须逐次确认。
- `system_sensitive` 默认不开放；若未来需要，必须独立设计和安全评审。
- Registry 不允许工具声明自己可以绕过系统权限或静默执行。

### 2.4 Registry 管理边界

- 初期采用代码内静态 Registry，避免运行时动态注入工具。
- 新工具必须经过代码评审、schema 测试和权限测试。
- 不允许模型创建、修改或启用 Registry 项。
- 工具下线应显式禁用，并保持旧审计记录可解释。
- 同名工具的破坏性 schema 变化必须提升版本。

## 3. Permission Gate

### 3.1 决策输入

Permission Gate 只使用结构化、可验证的信息：

- Tool Registry 定义。
- 调用参数的安全摘要。
- 用户已授予的 Runtime scope。
- 操作系统报告的权限状态。
- 当前设备身份和在线状态。
- 请求时间、过期时间和幂等键。
- 是否存在本次调用所需的即时确认。

禁止使用推断的用户情绪、亲密度、AI 人格或模型置信度代替用户授权。

### 3.2 决策结果

```json
{
  "decision": "allow | require_confirmation | deny",
  "reasonCode": "PERMISSION_GRANTED",
  "grantId": null,
  "expiresAt": null
}
```

Reason code 应为稳定白名单，例如：

- `TOOL_NOT_REGISTERED`
- `PLATFORM_UNSUPPORTED`
- `DEVICE_OFFLINE`
- `SYSTEM_PERMISSION_MISSING`
- `USER_CONFIRMATION_REQUIRED`
- `USER_DENIED`
- `GRANT_EXPIRED`
- `SCOPE_MISMATCH`
- `REQUEST_EXPIRED`
- `PERMISSION_GRANTED`

### 3.3 授权模型

- `per_call`：每次执行都需要确认，用于发送、删除、付款等操作。
- `session`：仅在短期、用户可见的活动会话内有效。
- `time_bounded`：在明确时间范围内允许特定低风险能力。
- `persistent_limited`：用户在系统设置页明确授权的固定低风险 scope。

授权必须绑定：

- 用户。
- 设备。
- tool name 和版本。
- 参数范围或资源 scope。
- 到期时间。

“允许读取日历”不能被解释为“允许修改日历”，“允许创建提醒”不能扩展为“允许发送消息”。

### 3.4 用户确认体验

确认界面至少显示：

- 哪个 Agent 请求操作。
- 将执行什么具体动作。
- 目标设备和目标资源。
- 将共享或修改哪些数据。
- 是否可撤销。
- 授权仅本次还是有明确期限。

拒绝、取消、超时均视为未授权。不得使用误导性按钮、预选同意或后台静默确认。

## 4. Device Bridge

### 4.1 职责

Device Bridge 是 Runtime 与操作系统能力之间的窄接口：

- 将平台无关工具参数转换为 Android/iOS 原生调用。
- 检查操作系统权限和设备能力。
- 展示必要的系统 UI 或本地确认。
- 返回受限结构化结果。
- 支持请求过期、取消、幂等和超时。

Bridge 不负责解释用户意图，不运行模型，不扩大 Permission Gate 的授权范围。

### 4.2 本地执行模型

建议在手机上运行一个用户可见的 Companion Mobile Agent：

- 使用应用沙箱保存设备密钥和最小配置。
- 通过平台官方 API 执行能力。
- 每次执行前再次校验 request signature、expiry、tool version 和 grant。
- 对高风险操作展示本地确认或跳转到系统确认界面。
- 在应用内提供最近执行记录、权限管理和一键停用。

### 4.3 能力适配

统一工具可以有不同平台实现：

```text
device.reminder.create
  -> AndroidReminderBridge
  -> IOSReminderBridge
```

平台不支持时返回 `PLATFORM_UNSUPPORTED`，不能通过私有 API、自动化点击或权限绕过模拟实现。

### 4.4 结果边界

Bridge 仅返回完成任务所需字段，例如：

```json
{
  "status": "succeeded",
  "resourceId": "opaque-local-id",
  "completedAt": "2026-07-20T12:00:00.000Z"
}
```

不得默认上传联系人全集、照片库、剪贴板、通知正文、设备 token 或系统日志。错误返回稳定 error code，不上传原生 stack 或包含敏感数据的 provider/system message。

## 5. Mobile Agent 通信方案

### 5.1 总体方案

推荐采用“VPS 控制面中继 + 设备主动建立加密连接 + 本地最终授权”的架构：

```text
AI Companion Runtime on VPS
        |
        | authenticated capability envelope
        v
VPS Relay / Queue
        ^
        | outbound TLS connection / push wake-up hint
        |
Android or iOS Mobile Agent
        |
        v
Local Permission Check -> Native OS API -> Visible Result
```

VPS Relay 只负责路由、短期排队和状态回传，不应持有可绕过设备确认的万能权限。

### 5.2 通信信封

请求建议包含：

- `requestId`
- `deviceId`
- `toolName`
- `toolVersion`
- schema 校验后的参数
- `createdAt`
- `expiresAt`
- `idempotencyKey`
- Permission Gate decision/grant reference
- Runtime signature

设备响应建议包含：

- `requestId`
- `status`
- 安全 result 或 error code
- `completedAt`
- Device Agent signature

每个请求必须防重放。过期、签名错误、设备不匹配或版本不兼容时直接拒绝。

### 5.3 Android

Android 可支持较丰富的后台和设备能力，但必须遵循版本与厂商限制：

- 优先使用官方 Intent、Activity Result API、Calendar/Contacts 等受控 provider API。
- 后台工作使用 WorkManager；需要持续运行时遵守 Foreground Service 类型和常驻通知要求。
- 使用系统运行时权限；敏感权限按用途逐项请求。
- 推送可用于提示设备拉取待处理请求，但推送 payload 不携带敏感参数。
- Accessibility、Device Admin、Notification Listener 等高权限能力不应作为默认方案。
- 不使用无障碍服务模拟点击来绕过应用或系统权限。

Android 仍不能被视为“可完全控制”。锁屏状态、后台限制、电池策略、权限撤销和 OEM 行为都可能阻止执行，系统应安全失败并返回明确状态。

### 5.4 iOS 限制

iOS 对后台执行和跨应用控制限制更严格，设计必须接受平台能力缺失：

- 使用公开框架、App Intents、Shortcuts、UserNotifications、EventKit 等官方能力。
- 许多动作需要应用前台、系统 UI 或用户确认。
- 后台执行时间有限，不能依赖永久后台 socket 或常驻进程。
- Push Notification 只能唤醒或提示有限流程，不能保证任意后台动作执行。
- 无法通用控制其他 App，也不能绕过联系人、日历、照片、位置等系统权限。
- 对不支持静默执行的操作，应返回 `USER_INTERACTION_REQUIRED` 并引导用户进入明确界面。

初期 iOS Capability 集应小于 Android 集，并在 Registry 中明确平台差异，不能为了功能对齐使用私有 API 或规避审核机制。

### 5.5 本地设备发现与配对

建议采用用户主动配对：

1. 用户在 VPS Companion Center 创建一次性配对请求。
2. Mobile Agent 扫描二维码或输入短期代码。
3. 双方交换公钥并显示设备名称和指纹摘要。
4. 用户在手机和控制面确认。
5. VPS 保存设备公钥和撤销状态；设备私钥留在系统安全存储中。

配对不自动授予任何 Capability。设备注册与工具授权是两个独立步骤。

### 5.6 VPS 中继

VPS Relay 的最小职责：

- 认证 Runtime 和设备连接。
- 保存短期、加密或最小化的待处理请求。
- 按 device ID 路由。
- 管理 acknowledgement、expiry 和幂等状态。
- 返回在线、已送达、等待确认、完成或失败状态。

VPS Relay 不应：

- 保存长期设备内容。
- 解密不需要由服务器理解的敏感参数。
- 代表设备绕过本地 Permission Gate。
- 在设备离线后无限期保留命令。
- 将一个设备的授权复用于另一设备。

可选的端到端加密方案应让 Runtime 和已配对设备持有会话密钥，中继只看到路由元数据。密钥轮换、设备撤销和丢失设备处理必须在实现前单独设计。

### 5.7 在线与离线行为

- 在线：设备通过出站连接接收通知并主动拉取请求。
- 短期离线：中继保存到 `expiresAt`，设备恢复后拉取。
- 请求过期：设备和中继均拒绝执行。
- 长期离线：返回明确失败，不自动改用其他设备。
- 网络重试：只重传相同 request ID，不重复执行；由幂等键保护。

## 6. 安全边界

### 6.1 明确禁止

- 默认完全控制手机。
- 绕过 Android、iOS 或其他操作系统权限。
- 隐藏执行行为、静默伪装操作或删除用户可见记录。
- 使用 Accessibility、私有 API、越狱/Root 能力绕过正常授权流程。
- 将模型自然语言直接映射为未校验的系统调用。
- 在没有明确 scope 的情况下复用或扩大授权。
- 将设备密钥、API token、Bearer token、完整请求参数或敏感执行结果写入日志。
- 自动读取聊天历史或 Memory content 作为设备操作参数。
- 根据关系等级、情绪推断或 AI 人格降低确认要求。

### 6.2 可见性与可撤销性

- Mobile Agent 必须提供当前连接状态、已授权能力、待确认请求和近期执行结果。
- 后台持续能力必须有符合平台规则的可见指示。
- 用户可以随时撤销单个 tool scope、断开设备或停用全部 Agent 能力。
- 撤销后，未执行请求立即失效；VPS Relay 不再投递。
- 可撤销操作应在结果中提供撤销入口或资源标识，但不得承诺系统无法保证的撤销能力。

### 6.3 审计边界

重要事实应通过 EventStore 记录，建议未来评审以下最小 Event：

- capability requested
- permission required/approved/denied
- dispatched
- succeeded/failed/expired
- device paired/revoked

Event payload 只保存 tool name、request ID、device ID 的非敏感标识、状态、reason code 和时间。不得保存原始消息、联系人内容、位置轨迹、文件内容、token、provider response 或 stack。

本设计不新增 Event 类型；具体定义留待后续实现任务明确授权。

### 6.4 故障安全

- Registry、Gate 或设备状态不可用时默认拒绝。
- 无法确认执行结果时返回 `unknown`，不能假定成功并再次执行高风险操作。
- 参数 schema 校验失败不下发设备。
- 设备端必须重复验证权限，不能信任 VPS 已授权就跳过本地检查。
- 时间漂移、签名异常、重放、重复 request ID 和版本不匹配均拒绝执行。

## 7. 后续实现路线

每个阶段必须独立评审和测试，不自动扩展到下一阶段。

### 阶段 1：Capability Domain Model

目标：定义纯本地的数据结构和静态 Tool Registry。

范围：

- Tool definition schema。
- Capability request/result schema。
- 风险等级与稳定 reason code。
- Registry 查询接口。

边界：不执行工具、不连接设备、不新增网络服务。

### 阶段 2：Permission Gate

目标：实现独立、可测试的权限决策组件。

范围：

- deny-by-default。
- per-call、session、time-bounded、persistent-limited scope。
- 请求过期、平台支持和系统权限状态校验。
- fake grant store 和 fake device state 测试。

边界：不调用模型、不接入真实 Android/iOS 权限。

### 阶段 3：Local Fake Device Bridge

目标：验证 dispatcher、幂等、超时、取消和结果过滤。

范围：

- 仅 fake adapter。
- 可预测的成功、拒绝、超时和重复请求测试。
- EventStore 审计设计的独立评审。

边界：不访问真实设备或外部服务。

### 阶段 4：VPS Relay 原型

目标：建立最小、认证、短期队列式的设备通信控制面。

范围：

- 配对协议原型。
- 签名 envelope、expiry、ack 和幂等。
- fake mobile client 端到端测试。
- 设备撤销和密钥轮换设计。

边界：不承载敏感正文，不接入真实手机能力。

### 阶段 5：Android 最小能力试点

目标：在用户可见的测试应用中接入一个低风险、易撤销能力。

候选：创建本地提醒草稿或打开预填充系统界面，由用户确认完成。

范围：

- 正式系统权限流程。
- 本地确认与执行历史。
- 前后台限制、离线和撤销测试。

边界：不接入 Accessibility、Device Admin、自动发送消息、删除或付款能力。

### 阶段 6：iOS 最小能力试点

目标：使用公开 API 和系统 UI 接入一个平台允许的低风险能力。

候选：App Intent/Shortcut 或提醒草稿流程。

范围：

- 明确前台与用户交互要求。
- Push 唤醒限制测试。
- 平台不支持时的安全降级。

边界：不使用私有 API，不追求与 Android 的强制功能对齐。

### 阶段 7：有限生产化

目标：在明确用户授权下开放经过评审的少量工具。

前置条件：

- Threat model 和隐私评审完成。
- 密钥管理、设备撤销、审计和事故响应到位。
- 每个工具都有权限、schema、幂等、故障和敏感字段测试。
- Companion Center 提供清晰的设备与授权管理界面。
- 所有外部测试使用专用测试设备和测试账户。

任何新增高风险工具必须作为独立任务设计，不因 Capability Layer 已存在而自动获得实现授权。

## 当前结论

P6-9.13 应从 Explanation Layer 重新规划为 Agent Capability Layer，但当前阶段仅完成架构设计。尚未实现 Tool Registry、Permission Gate、Device Bridge、VPS Relay、Mobile Agent、API、MCP、Event、数据库表或 migration，也未接入任何 Android 或 iOS 设备。
