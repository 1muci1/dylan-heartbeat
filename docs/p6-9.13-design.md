# P6-9.13 Proactive Explanation Layer Design

## 1. 目标

Proactive Explanation Layer 为一次主动互动提供安全、可追溯、只读的结构化解释，回答以下问题：

- 为什么系统考虑发起这次主动互动？
- Behavior Policy 和 Wake Decision 给出了什么结构化结论？
- 是否创建了 AI Job，Job 当前处于什么状态？
- 是否创建并发送了 Delivery，或者为什么失败、被阻止或等待中？
- 用户是否已对该 Delivery 提交明确反馈？

该层只聚合现有事实，不生成新事实，不重新执行决策，不调用模型，也不改变任何业务状态。解释内容必须来自已有结构化字段，并使用稳定的公共 reason code 表达，不能推断用户情绪、关系含义、人格变化或模型思考过程。

本阶段的设计对象是按 ID 查询单次主动互动解释。实现前需要明确 `:id` 的标识语义及跨数据源关联规则；建议将其定义为 Delivery ID，因为 Delivery 已经关联 AI Job 和触发 Event，且反馈也以 Delivery ID 为唯一关联键。

## 2. 数据来源

### Behavior Policy

用途：解释候选是否满足主动互动规则，以及结构化的允许或阻止原因。

允许读取：

- 已有规则结果中的 `allowed`、`action`、`reasonCode`、`priority` 等公共结构化字段。
- 已持久化或已存在于安全快照中的规则结论。

限制：Explanation Layer 不重新计算或修改 Behavior Policy，不读取用于模型生成的原始上下文，不根据反馈自动调整规则。

### Wake Decision

用途：展示 Wake Decision 的模式、最终结论和公共原因码，区分 legacy、shadow、enforced 等已有运行结果。

允许读取：

- 已有安全快照或公开 Dashboard View 中的模式、decision、reason code 和必要时间字段。
- 与目标主动互动有明确关联的结构化决策事实。

限制：不重新运行 evaluator、Gate 或 Rollout，不改变分流，不读取内部调试数据。如果当前系统没有按 Delivery 持久化 Wake Decision 关联，则返回“不可用”，不能根据当前指标反推历史决策。

### AI Job

用途：说明主动响应 Job 是否创建、排队、运行、完成、失败或取消。

允许读取：

- Job ID、Job 类型、公共状态、attempt count、created/completed 时间和安全错误码。
- Delivery 已有的 `jobId` 关联。

限制：不返回输入内容、生成结果正文、模型名称、provider、usage、错误消息、prompt 或内部任务上下文。

### Delivery

用途：作为解释查询的主要锚点，说明渠道、状态、创建/发送/失败时间、attempt count、reason code 和安全的最后错误码。

允许读取：

- `id`
- `channel`
- `status`
- `reasonCode`
- `attemptCount`
- `createdAt`
- `sentAt`
- `failedAt`
- 经白名单确认的 `lastErrorCode`

限制：不返回 Delivery `text`、锁、worker、Retry 时间、dedupe key、provider 数据或内部字段。Explanation 查询不得修改 Delivery 状态，也不得触发 send、retry 或 cancel。

### Feedback

用途：说明用户是否已对该 Delivery 提交明确反馈。

允许读取：

- `feedbackType`
- `createdAt`

允许的类型仅为：

- `liked`
- `dismissed`
- `not_relevant`
- `disable_future`

限制：不输出用户画像、心理解释或关系影响。反馈不存在时返回 `null`，不能将“无反馈”解释为忽略或不喜欢。

## 3. 明确禁止访问的数据

Explanation Layer 在查询、聚合、日志、错误和响应中均禁止访问或输出：

- Memory content
- chat history
- prompt
- model reasoning
- token，包括 API token、Bearer token 和模型 token 数据
- provider response

同时禁止以间接方式恢复这些内容，例如读取包含原始正文的 AI Job input/output、Delivery text、Event 未过滤 payload、错误 message/stack 或 provider 调试字段。

实现应通过窄接口或字段白名单读取数据，而不是先读取完整对象再依赖最终 JSON 序列化过滤。日志只能记录安全的错误分类和必要的请求关联信息，不记录上述禁止内容。

## 4. HTTP API 设计草案

### Endpoint

```http
GET /api/v1/proactive/explanations/:id
Authorization: Bearer GATEWAY_API_KEY
```

建议 `:id` 为 Delivery ID。不存在的 Delivery 返回 `404`；格式错误返回 `400`；认证失败返回 `401`；未配置 Gateway key 返回 `503`。

### 建议响应

```json
{
  "id": "delivery-id",
  "summaryCode": "DELIVERY_SENT",
  "policy": {
    "available": true,
    "allowed": true,
    "reasonCode": "FOLLOW_UP"
  },
  "wakeDecision": {
    "available": false,
    "mode": null,
    "decision": null,
    "reasonCode": null
  },
  "aiJob": {
    "id": "job-id",
    "type": "proactive_response",
    "status": "completed",
    "attemptCount": 1,
    "createdAt": "2026-07-20T10:00:00.000Z",
    "completedAt": "2026-07-20T10:00:01.000Z",
    "errorCode": null
  },
  "delivery": {
    "id": "delivery-id",
    "channel": "push",
    "status": "sent",
    "reasonCode": "FOLLOW_UP",
    "attemptCount": 1,
    "createdAt": "2026-07-20T10:00:01.000Z",
    "sentAt": "2026-07-20T10:00:02.000Z",
    "failedAt": null,
    "lastErrorCode": null
  },
  "feedback": null
}
```

设计说明：

- `summaryCode` 是规则化、非生成式的总结码，由已有事实映射产生，不是自然语言模型解释。
- 子对象只在存在可靠关联时填充；无法证明的历史信息使用 `available:false` 或 `null`，不得推测。
- 响应不包含完整 Event 列表，避免泄露内部 payload 和用户行为细节。
- Endpoint 仅注册 GET，不增加 POST、PUT、PATCH 或 DELETE。
- 查询不创建 Event，不修改访问计数或任何业务表。

### 建议 summaryCode 白名单

- `DELIVERY_PENDING`
- `DELIVERY_SENDING`
- `DELIVERY_SENT`
- `DELIVERY_FAILED`
- `DELIVERY_CANCELLED`
- `FEEDBACK_RECORDED`
- `EXPLANATION_PARTIAL`

最终白名单应在实现规格确认后固定。`summaryCode` 只描述可验证的系统状态，不表达用户情绪或关系判断。

## 5. MCP 设计

建议新增只读工具：

```text
proactive_explanation_get
```

输入草案：

```json
{
  "id": "delivery-id"
}
```

Schema 草案：

- `id`：必填、非空字符串，长度受限，并与 HTTP 的 Delivery ID 校验保持一致。
- 不接受 `includeText`、`includePrompt`、`debug`、`raw`、`reasoning` 等扩展参数。

Annotations：

```text
readOnlyHint: true
destructiveHint: false
idempotentHint: true
openWorldHint: false
```

输出与 HTTP View 使用相同公共 schema，并在 MCP 层再次执行字段白名单映射。MCP 工具通过现有认证 HTTP client 读取 Explanation API，不直接访问数据库，不增加 proactive send、retry、cancel、feedback write 或设置写入工具。

MCP 是否在本阶段落地，应以最终实现任务的明确授权为准；本设计不自动改变现有 MCP 权限模型。

## 6. 安全边界

- 只读：不写 Event、State、Memory、Delivery、Feedback 或 AI Job。
- 非生成式：不调用模型，不生成自由文本解释，不读取 model reasoning。
- 不重放决策：不调用 Behavior Policy、Wake Decision evaluator、Gate、Rollout、Worker、Retry Policy 或 Bark Adapter 执行业务动作。
- 不推断：缺失数据返回 `null`/`available:false`，不从反馈、失败或沉默推断情绪、人格或关系状态。
- 最小关联：只沿 Delivery ID 的明确外键或已持久化关联查询，不进行模糊匹配。
- 字段白名单：每个数据源单独映射公共字段；禁止透传 Store 内部对象。
- 错误最小化：公共错误不包含 SQL、stack、provider message、URL、token 或内部标识。
- 认证一致：HTTP 使用 `Bearer GATEWAY_API_KEY`；MCP 继续通过受限 API client。
- 兼容性：不修改 Behavior Policy、Wake Decision、Rollout、Delivery Worker、Retry、Bark Adapter、Memory Pipeline 或现有 MCP 工具语义。
- 无新事实：查询本身不创建 Explanation Event，也不保存查询历史。

## 7. 测试计划

### View 单元测试

1. sent、failed、pending、sending、cancelled Delivery 映射到稳定 summary code。
2. AI Job、Delivery、Feedback 字段按白名单聚合。
3. Behavior Policy 或 Wake Decision 关联不存在时返回不可用，不进行推断。
4. Feedback 不存在时返回 `null`，各白名单反馈原样返回。
5. Delivery 不存在时返回明确的 not found error。
6. 所有响应最多包含设计 schema 中的字段。

### HTTP 测试

1. 无 Bearer token、错误 token 和缺失 Gateway key 被拒绝。
2. 合法 GET 返回与 View 相同的安全结构。
3. 非法或不存在 ID 被拒绝。
4. POST、PUT、PATCH、DELETE 路由不存在。
5. 响应不包含 text、prompt、reasoning、token、provider response、stack、锁或内部字段。

### MCP 测试

1. `proactive_explanation_get` 可发现。
2. input schema 只包含必填 `id`。
3. annotations 保持完整只读声明。
4. MCP 输出与 HTTP 公共 schema 一致并再次过滤敏感字段。
5. 不出现 send、retry、cancel 或其他写工具。

### 不变性与副作用测试

1. 查询前后 Event、State、Memory、Delivery、Feedback 和 AI Job 数据不变化。
2. 不调用模型或 AI Adapter。
3. 不调用 Bark/Push Adapter。
4. 不调用 Wake Decision evaluator、Gate 或 Rollout。
5. 不调用 Delivery Worker、claim、mark、retry 或 cancel 方法。
6. 不读取 Memory content、chat history、prompt、model reasoning、token 或 provider response。
7. 日志中不出现敏感值和 stack。
