# P6-9.13 Proactive Explanation MCP Server Design

## 1. 背景与目标

P6-9.13 第一阶段已经实现：

- 以 Delivery ID 为锚点的 `ProactiveExplanationView`。
- 认证只读接口 `GET /api/v1/proactive/explanations/:deliveryId`。
- 静态 Tool Registry 中的 `proactive_explanation_get` 定义。
- Delivery、AI Job、Trigger Event 和 Feedback 的字段白名单输出。

本阶段已将该查询接入现有本地只读 MCP Server。MCP Tool 通过现有受认证 HTTP client 调用 Explanation GET API，不直接访问 Store、数据库或业务模块。

本阶段不新增写能力、不调用模型、不新增 migration、不接入外部 MCP 服务，也不改变 Explanation、Delivery、Event、State、Memory、Device 或 Android 的业务语义。

## 2. MCP Tool 定义

### 2.1 Tool name

```text
proactive_explanation_get
```

该名称必须与静态 Tool Registry 中已经注册的名称完全一致。不得增加别名，也不得另行注册 `proactive.explanation.get` 等同义名称。

### 2.2 Input schema

```json
{
  "type": "object",
  "properties": {
    "deliveryId": {
      "type": "string",
      "minLength": 1,
      "maxLength": 200
    }
  },
  "required": ["deliveryId"],
  "additionalProperties": false
}
```

输入约束：

- `deliveryId` 必填。
- 必须为字符串，trim 后长度为 1～200。
- 不接受 `includeText`、`raw`、`debug`、`reasoning`、`includePayload` 或任何其他字段。
- MCP handler 不修改调用方输入。
- HTTP client 对 ID 使用 `encodeURIComponent` 构造固定路径，不允许调用方提供 URL、query string 或相对路径。

### 2.3 Output schema

成功输出固定为：

```json
{
  "deliveryId": "opaque-delivery-id",
  "summaryCode": "DELIVERY_SENT",
  "delivery": {
    "status": "sent",
    "channel": "push",
    "reasonCode": "FOLLOW_UP",
    "attemptCount": 1,
    "createdAt": "2026-07-22T10:00:00.000Z",
    "sentAt": "2026-07-22T10:00:02.000Z",
    "failedAt": null,
    "lastErrorCode": null
  },
  "aiJob": {
    "available": true,
    "id": "opaque-job-id",
    "status": "completed"
  },
  "triggerEvent": {
    "available": true,
    "eventType": "proactive.delivery_sent",
    "occurredAt": "2026-07-22T10:00:02.000Z"
  },
  "wakeDecision": {
    "available": false,
    "decision": null,
    "reasonCode": null
  },
  "feedback": {
    "feedbackType": "liked",
    "createdAt": "2026-07-22T11:00:00.000Z"
  }
}
```

允许的 `summaryCode`：

- `DELIVERY_PENDING`
- `DELIVERY_SENDING`
- `DELIVERY_SENT`
- `DELIVERY_FAILED`
- `DELIVERY_CANCELLED`

允许的 Delivery `status`：

- `pending`
- `sending`
- `sent`
- `failed`
- `cancelled`

允许的 Feedback `feedbackType`：

- `liked`
- `dismissed`
- `not_relevant`
- `disable_future`

可选事实的形状必须稳定：

- AI Job 不可用时返回 `{ "available": false, "id": null, "status": null }`。
- Trigger Event 不可用时返回 `{ "available": false, "eventType": null, "occurredAt": null }`。
- Wake Decision 当前固定返回 `{ "available": false, "decision": null, "reasonCode": null }`，不得从当前指标反推历史决策。
- Feedback 不存在时返回 `null`。

MCP 返回使用 SDK 的标准双通道结构：

```json
{
  "content": [{ "type": "text", "text": "<structuredContent 的 JSON>" }],
  "structuredContent": {}
}
```

`content[0].text` 必须是 `structuredContent` 的 JSON 序列化结果，两者不得出现不同字段集合。

### 2.4 Annotations

必须复用现有 MCP Server 的完整只读 annotations：

```json
{
  "readOnlyHint": true,
  "destructiveHint": false,
  "idempotentHint": true,
  "openWorldHint": false
}
```

不得声明 destructive、open world 或非幂等语义。

## 3. 与现有 `proactive_explanation_get` 的关系

### 3.1 单一 schema 来源

Tool name、input schema、公共输出字段和 mapper 已收敛为一个共享的 Explanation contract，供以下边界共同使用：

```text
Shared Proactive Explanation Contract
    |-- Tool Registry input metadata
    |-- HTTP/View public output mapper
    |-- MCP Zod input adapter
    |-- MCP output mapper
    `-- contract tests
```

共享 contract 只包含：

- Tool name。
- input schema 和长度常量。
- summary/status/feedback 白名单。
- 公共输出字段映射与 JSON-safe 校验。

共享 contract 不执行查询，不访问数据库，不调用 HTTP，不保存状态，也不依赖 MCP transport。

Tool Registry 继续是 Tool 元数据的公共发现入口；MCP 注册必须读取或验证同一 contract，不能手写另一份名称、长度或 required 字段定义。

MCP SDK 使用 Zod，而 Registry 使用 JSON schema。Zod schema 可以是共享 contract 的窄适配器，但必须通过测试证明以下内容一致：

- Tool name 相同。
- 只有 `deliveryId` 一个输入字段。
- required、minLength、maxLength 和 unknown-field rejection 相同。

不得引入通用、不受控的 JSON Schema 执行器。只为本 Tool 做显式、可测试的窄适配。

### 3.2 防止 HTTP/MCP 漂移

必须建立 contract 测试：

1. Tool Registry 与 MCP 注册的 tool name 相同。
2. Registry input schema 与 MCP Zod 接受/拒绝的输入集合一致。
3. HTTP 成功响应经过共享公共 mapper 后，与 MCP `structuredContent` 深度相等。
4. HTTP 响应增加未知字段时，MCP 丢弃该字段，而不是自动扩展输出。
5. MCP 输出缺少 contract 必填字段或包含非法枚举时，安全失败，不返回部分透传对象。
6. `content[0].text` 反序列化后与 `structuredContent` 深度相等。

HTTP 是数据查询边界，MCP 是消费适配边界；两者共享 contract，但 MCP 不应直接透传任意 HTTP JSON。

## 4. 权限边界

### 4.1 只读

`proactive_explanation_get` 只查询已经存在的结构化事实：

- 不创建或更新 Delivery。
- 不创建 Event。
- 不修改 State、Memory、Feedback 或 AI Job。
- 不调用 Wake Decision evaluator、Gate 或 Rollout。
- 不调用模型或 AI Adapter。
- 不调用 Delivery Worker、Retry Policy 或 Bark Adapter。
- 不调用 Device Command、Android Provider 或 Android Companion。

### 4.2 无 Approval

该 Tool 不产生副作用，因此不进入 Tool Approval 流程：

- 不接受 `approvalId`。
- 不创建 pending Approval。
- 不调用 `ToolExecutionGateway` 的写执行路径。
- 不记录 `tool.requested`、`tool.approved`、`tool.completed` 或 `tool.failed` Audit Event。

MCP 的 API Bearer 认证是服务访问认证，不是用户对写操作的 Approval，二者不得混淆。

### 4.3 无 write capability

本阶段只注册一个 get Tool。禁止同时或隐式增加：

- proactive send、retry 或 cancel。
- feedback record。
- proactive settings update。
- Delivery mutation。
- Event、State 或 Memory 写入。
- Device/Reminder Draft Tool。

MCP Server 仍不得暴露通用 HTTP、SQL、URL fetch 或任意 Tool execution 能力。

## 5. 数据边界

### 5.1 允许返回字段

顶层：

- `deliveryId`
- `summaryCode`
- `delivery`
- `aiJob`
- `triggerEvent`
- `wakeDecision`
- `feedback`

Delivery：

- `status`
- `channel`
- `reasonCode`
- `attemptCount`
- `createdAt`
- `sentAt`
- `failedAt`
- `lastErrorCode`

AI Job：

- `available`
- `id`
- `status`

Trigger Event：

- `available`
- `eventType`
- `occurredAt`

Wake Decision：

- `available`
- `decision`
- `reasonCode`

Feedback：

- `feedbackType`
- `createdAt`

### 5.2 禁止返回字段

禁止在成功、错误、日志、MCP text content 或 structured content 中返回：

- Delivery `text`、`dedupeKey`、`jobId`、`eventId`。
- `lockedAt`、`lockOwner`、`nextRetryAt`、`maxAttemptCount` 等 Worker/Retry 内部字段。
- AI Job input、output、prompt、provider、model、usage、error message 或 stack。
- Event payload、source、dedupe/correlation/causation 内部字段。
- Feedback ID 或其他用户行为细节。
- Memory content、聊天全文、prompt、model reasoning。
- API token、Bearer token、URL、请求 headers。
- provider response、系统错误 message、SQL 或 stack。

MCP 必须在 HTTP 已过滤的基础上再次构造全新的白名单对象，不使用对象展开或递归透传。

## 6. 错误处理

所有错误通过现有 MCP `isError` 结构返回，错误内容为稳定 code 和安全 message：

```json
{
  "isError": true,
  "content": [{
    "type": "text",
    "text": "{\"error\":{\"code\":\"DELIVERY_NOT_FOUND\",\"message\":\"Delivery 不存在\"}}"
  }],
  "structuredContent": {
    "error": {
      "code": "DELIVERY_NOT_FOUND",
      "message": "Delivery 不存在"
    }
  }
}
```

### 6.1 Missing delivery

HTTP `404` 或错误码 `DELIVERY_NOT_FOUND` 映射为：

```json
{
  "code": "DELIVERY_NOT_FOUND",
  "message": "Delivery 不存在"
}
```

不得返回原始 Store message、请求 URL 或 Delivery 内部字段。

### 6.2 Unavailable explanation

HTTP `5xx`、`PROACTIVE_EXPLANATION_UNAVAILABLE`、无效 JSON 或不符合输出 contract 的响应统一映射为：

```json
{
  "code": "EXPLANATION_UNAVAILABLE",
  "message": "Proactive Explanation 服务暂时不可用"
}
```

可选子事实缺失不是整个 Explanation 失败；它们继续使用 `available:false` 或 `null`。只有顶层 Delivery 不存在、顶层结构非法或查询服务失败才返回 MCP error。

### 6.3 Auth failure

HTTP `401`、`403` 或 `UNAUTHORIZED` 映射为：

```json
{
  "code": "UNAUTHORIZED",
  "message": "Proactive Explanation API 认证失败"
}
```

HTTP `503 GATEWAY_KEY_MISSING` 属于服务配置问题，对 MCP 映射为：

```json
{
  "code": "EXPLANATION_UNAVAILABLE",
  "message": "Proactive Explanation 服务暂时不可用"
}
```

错误日志只能包含稳定 error name/code；禁止记录 token、HTTP response、URL、headers 或 stack。

## 7. MCP Server / HTTP Client 边界

调用链固定为：

```text
MCP client
    -> local stdio MCP Server
    -> proactive_explanation_get handler
    -> MemoryApiClient.proactiveExplanation(deliveryId)
    -> authenticated GET /api/v1/proactive/explanations/:deliveryId
    -> ProactiveExplanationView
    -> existing read-only Stores
```

### 7.1 MCP Server 职责

- 注册 `proactive_explanation_get`。
- 使用共享 contract 的窄 Zod 适配验证输入。
- 调用 HTTP client 的专用方法。
- 对 HTTP 结果再次执行公共字段白名单映射。
- 将安全错误映射为 MCP `isError`。
- 复用现有只读 annotations 和 stdio transport。

MCP Server 不访问数据库，不 import Delivery/Event/AI Job/Feedback Store，不调用模型，也不执行业务状态转换。

### 7.2 HTTP Client 职责

- 新增专用只读方法，例如 `proactiveExplanation(deliveryId)`。
- 验证并 trim Delivery ID。
- 只构造固定前缀 `/api/v1/proactive/explanations/` 下的单个 GET 路径。
- 使用 `encodeURIComponent` 编码 ID。
- 复用既有 base URL、Bearer token、JSON 解析和状态码处理。
- 将非 JSON、非 2xx 和公共 API error 转换为稳定 client error。

HTTP client 的路径 allowlist 只增加 Explanation GET 的精确模式。不得开放任意 `/api/v1/proactive/*`、任意 URL 或任意 HTTP method。

### 7.3 外部边界

本阶段不接入外部 MCP Server 或远程 Tool Catalog。现有 MCP 进程继续使用本地 stdio transport；HTTP client 只连接已配置的现有 Gateway API base URL。

不得把 Gateway API token 放入 Tool 输入、输出、日志或错误。MCP Tool 调用方无法选择 base URL 或 token。

## 8. 数据持久化边界

本阶段不新增或修改持久化数据：

- 不新增 migration、表、字段或索引。
- 不保存 MCP 查询记录。
- 不创建 Tool Audit Event。
- 不修改 Delivery、Feedback、AI Job、Event、State 或 Memory。
- 不缓存完整 Explanation 响应。

查询继续使用现有 Explanation HTTP API 和既有 Store 数据。MCP 层不能绕过 HTTP API 直接查询 SQLite。

## 9. 测试计划

所有测试使用 fake HTTP client 或 fake fetch；禁止访问真实 Gateway、真实模型、真实 Bark、真实 Android 设备或外部 MCP 服务。

### 9.1 Tool 定义测试

1. MCP Server 只注册一个名称完全匹配的 `proactive_explanation_get`。
2. Tool Registry 与 MCP name、description、deliveryId required/min/max 约束一致。
3. annotations 精确等于四个只读声明。
4. 空 ID、空白 ID、超长 ID、非字符串和额外字段被拒绝。
5. 输入对象不被修改。

### 9.2 HTTP client 测试

1. 合法 ID 只发起一次认证 GET 请求。
2. ID 使用 `encodeURIComponent`，不能注入 query、fragment 或其他路径。
3. 路径 allowlist 只接受 Explanation GET 精确前缀和单个 ID。
4. 请求包含现有 Bearer token，但测试日志和错误不包含 token。
5. 401/403、404、503、5xx、无效 JSON 和 API error 分别映射到稳定 client error。
6. 不允许 POST、PUT、PATCH、DELETE 或调用任意 URL。

### 9.3 输出 contract 测试

1. 每个 Delivery status 映射的 Explanation 均能输出。
2. AI Job、Trigger Event、Wake Decision 不可用形状保持稳定。
3. Feedback 为 `null` 或四个白名单值之一。
4. HTTP 响应中注入未知字段时 MCP 丢弃未知字段。
5. 注入 Delivery text、provider、model、payload、token、URL、锁和 stack 时均不出现在 MCP 输出。
6. 非法 summary/status/feedback 枚举安全失败。
7. `content` JSON 与 `structuredContent` 深度一致。

### 9.4 错误测试

1. Missing Delivery 返回 `DELIVERY_NOT_FOUND`。
2. 顶层 Explanation 不可用返回 `EXPLANATION_UNAVAILABLE`。
3. 401/403 返回 `UNAUTHORIZED`。
4. Gateway key 缺失和其他配置错误不暴露内部配置。
5. 错误不包含响应正文、URL、token、provider message 或 stack。

### 9.5 副作用与回归测试

1. MCP 调用前后数据库、Event、State、Memory、Delivery、Feedback 和 AI Job 不变化。
2. 不调用模型、Wake Decision、Delivery Worker、Bark、Device Command 或 Android transport。
3. MCP Server 不 import database 或业务 Store。
4. 现有 Memory、State、Relationship、Proactive Overview 和 Tool Audit MCP 工具保持只读且测试通过。
5. 现有 Explanation HTTP、Tool Registry、Reminder Draft 和全量 Node 测试保持通过。
6. 运行 `npm test` 和 `git diff --check`。

## 10. 第一阶段实现状态

第一阶段已经完成：Explanation GET API、MCP Tool、静态 Tool Registry 和受认证 HTTP client 复用同一个 shared contract；HTTP 与 MCP 通过同一公共 mapper 保持 schema 一致。

实现保持为现有本地只读 MCP Server 的窄扩展：共享 contract 防止 schema 漂移，HTTP client 只开放精确 GET 路径，MCP 再次执行字段白名单映射。无 Approval、无写能力、无新 Event、无 migration、无数据库变化、无 Device/Android 参与，也不接入外部 MCP 服务。

仍未实现且不属于第一阶段范围：Companion Center UI、逐 Delivery Wake Decision 可靠关联、模型生成的解释，以及任何 Reminder Draft 或 Reminder 执行能力。
