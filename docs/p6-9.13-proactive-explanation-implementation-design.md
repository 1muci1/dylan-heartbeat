# P6-9.13 Proactive Explanation Layer Implementation Design

## 实现状态

P6-9.13 第一阶段已实现。

实际完成范围：

- 新增 `ProactiveExplanationView`，以 Delivery ID 为锚点只读聚合 Delivery、AI Job、Trigger Event 和 Feedback。
- 对 `pending`、`sending`、`sent`、`failed`、`cancelled` 建立稳定 summary code 映射。
- 缺失的可选关联返回 `available:false` 或 `null`，不反推历史事实。
- 新增认证只读接口 `GET /api/v1/proactive/explanations/:deliveryId`。
- 新增 `proactive_explanation_get` Tool 定义并接入静态 Tool Registry。
- 保持响应字段白名单，不返回 Delivery 正文、Event payload、AI Job provider/model/error message 或内部锁与重试字段。
- 新增读取层、HTTP API、安全边界和 Tool Registry 测试；Node 全量测试通过。

第一阶段尚未实现：

- `proactive_explanation_get` 尚未注册到 MCP Server，也未接入 MCP HTTP client。
- Companion Center 尚未增加 Explanation UI。
- Wake Decision 没有可靠的逐 Delivery 历史关联，当前固定返回 `available:false`。
- 没有自然语言解释、模型调用、发送、Retry、Cancel 或设置写能力。
- 没有新增 Event、State/Memory 写入、migration、数据库字段、Device Command 或 Android 变化。

## 1. 背景和目标

Roadmap 将 P6-9.13 Proactive Explanation Layer 标记为 `READY`。本阶段在已完成 P6-9.38 Reminder Draft Integration 的系统基础上补齐只读解释边界，不继续增加 Android 写能力。

当前系统已经保存 Delivery、AI Job、Event、State、Relationship、Wake Decision 和用户明确 Feedback 等结构化事实，但缺少一个面向 Companion Center 的窄查询，将一次主动行为的当前结果和可证明原因安全地聚合起来。

本阶段目标是增加按 Delivery ID 查询的结构化解释能力，回答：

- Delivery 当前是等待、发送中、已发送、失败还是已取消。
- Delivery 记录了哪个公共 `reasonCode`。
- 是否存在可可靠关联的 AI Job、触发 Event 和用户明确 Feedback。
- 某一部分事实无法可靠关联时，明确返回不可用，而不是从当前状态反推历史决策。

解释必须完全来自现有结构化事实。它不调用模型，不生成自由文本解释，不重新运行 Behavior Policy、Wake Decision 或 Rollout，也不创建新的系统事实。

查询锚点固定为 Delivery ID。现有 Delivery 已保存 `jobId`、可选 `eventId`、状态和公共 reason code；Feedback 也以 Delivery ID 关联，因此不需要模糊匹配。

## 2. 不包含的能力

本阶段不包含：

- 主动消息发送、重发、取消或人工 Retry。
- 修改 proactive contact 设置或绕过 Proactive Send Gate。
- 重新执行 Behavior Policy、Wake Decision、Rollout、AI Job 或 Delivery Worker。
- 调用模型生成自然语言解释、总结或 reasoning。
- 读取或返回 Delivery 正文、聊天全文、prompt、Memory content 或 provider response。
- 推断用户情绪、意图、亲密度、人格或关系变化。
- 创建、修改或删除 Event、State、Memory、Delivery、Feedback 或 AI Job。
- 新增 HTTP 写接口或 MCP 写工具。
- Device Tool、设备控制、Reminder Draft 查询或 Android 系统能力。
- 新增 migration、表、列、索引或持久化缓存。
- 接入 Bark、真实模型、真实 Android API 或其他外部服务。

## 3. Tool 定义

### 3.1 公共查询接口

第一阶段已新增只读 HTTP 查询：

```http
GET /api/v1/proactive/explanations/:deliveryId
Authorization: Bearer GATEWAY_API_KEY
```

`:deliveryId` 必须是非空字符串，trim 后长度为 1～200。不存在的 Delivery 返回 `404`；非法输入返回 `400`；认证失败沿用现有认证错误。

只允许 GET。不得注册 POST、PUT、PATCH 或 DELETE。

### 3.2 MCP Tool

第一阶段已将以下定义接入静态 Tool Registry；MCP Server 注册留待后续阶段：

```json
{
  "name": "proactive_explanation_get",
  "description": "Return a structured read-only explanation for one proactive delivery.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "deliveryId": {
        "type": "string",
        "minLength": 1,
        "maxLength": 200
      }
    },
    "required": ["deliveryId"],
    "additionalProperties": false
  }
}
```

Annotations 必须为：

```text
readOnlyHint: true
destructiveHint: false
idempotentHint: true
openWorldHint: false
```

MCP handler 必须通过现有受认证 HTTP client 调用公共查询，不能直接访问数据库。

该查询不注册到 Agent Tool Registry 的 `device_bridge` 执行链。它属于当前 MCP 只读查询面，不得被包装成可产生副作用的 Agent Tool。

### 3.3 输出 schema

建议公共响应：

```json
{
  "deliveryId": "opaque-delivery-id",
  "summaryCode": "DELIVERY_SENT",
  "delivery": {
    "status": "sent",
    "channel": "push",
    "reasonCode": "FOLLOW_UP",
    "attemptCount": 1,
    "createdAt": "2026-07-22T10:00:00.000Z",
    "sentAt": "2026-07-22T10:00:02.000Z",
    "failedAt": null,
    "lastErrorCode": null
  },
  "aiJob": {
    "available": true,
    "id": "opaque-job-id",
    "status": "completed"
  },
  "triggerEvent": {
    "available": false,
    "eventType": null,
    "occurredAt": null
  },
  "wakeDecision": {
    "available": false,
    "decision": null,
    "reasonCode": null
  },
  "feedback": null
}
```

`summaryCode` 只能使用固定白名单：

- `DELIVERY_PENDING`
- `DELIVERY_SENDING`
- `DELIVERY_SENT`
- `DELIVERY_FAILED`
- `DELIVERY_CANCELLED`
- `EXPLANATION_PARTIAL`

`summaryCode` 只映射 Delivery 的可验证状态，不表达模型意图或用户心理。若 Delivery 存在但关键关联无法安全读取，可使用 `EXPLANATION_PARTIAL`；不得把缺失数据填成推测值。

每个子对象必须先做字段白名单映射。禁止先返回 Store 完整对象再依赖最终序列化过滤。

明确禁止输出：

- Delivery `text`、`dedupeKey`、`lockedAt`、`lockOwner`、`nextRetryAt`、`maxAttemptCount`。
- AI Job input、output、prompt、模型、provider、usage、原始错误和 stack。
- Event 原始 payload；只允许经 Event 公共边界确认的类型和时间字段。
- Feedback ID；只允许白名单 `feedbackType` 和 `createdAt`。
- token、URL、凭据、聊天内容和 Memory content。

## 4. Approval 要求

本能力是认证后的只读查询，不产生外部副作用，因此不创建 Tool Approval，也不接受 `approvalId`。

边界如下：

- HTTP 继续使用现有 Bearer 认证。
- MCP 继续通过受限 API client 使用相同认证边界。
- 不调用 `ToolExecutionGateway`、`CapabilityPolicy` 或 `ToolApprovalStore`。
- 不允许以“已批准查询”为由扩展到 send、retry、cancel、feedback 或设置写入。
- 如果未来加入任何写动作，必须定义独立 Tool、独立 schema 和独立 Approval 设计，不能复用本查询授权。

## 5. Audit / Event 行为

本阶段不新增 Event 类型，也不记录“解释被查询”事件。

原因：查询本身不是重要业务状态变化，记录查询事实会扩大 Event 范围并可能形成不必要的用户行为日志。

实现只读取已有事实：

- Delivery 状态及公共 reason code。
- Delivery 明确关联的 AI Job ID 和 Event ID。
- Delivery ID 对应的明确 Feedback。
- 已存在且能通过窄接口安全读取的决策事实。

不得：

- 直接写 `events` 表。
- 调用 `EventStore.create()` 记录查询。
- 返回完整 Event payload。
- 从当前 Wake Decision 指标反推某个历史 Delivery 的决策。
- 在日志中记录响应、内部对象、错误 stack 或敏感字段。

日志仅允许记录稳定错误分类和必要的请求关联 ID；不得记录正文、prompt、Memory、provider response 或认证信息。

## 6. State / Memory 影响

本阶段对 State 和 Memory 都没有写影响：

- 不创建或更新 Companion State。
- 不调用 State Projector。
- 不修改 proactive contact 设置。
- 不读取或写入 Memory content。
- 不创建 Memory 候选或 AI Memory Job。
- 不修改 Relationship View 或关系等级。

如果解释需要展示某个 State 或 Relationship 结论，只能通过现有公共只读 view 获取已经过滤的结构化字段；第一版应优先省略无法与 Delivery 明确关联的字段，而不是扩大读取范围。

## 7. Device Command Channel 是否参与

Device Command Channel 不参与本阶段。

查询链路应为：

```text
Companion Center / MCP
    -> authenticated read-only HTTP route
    -> ProactiveExplanationView
    -> DeliveryStore narrow read
    -> optional AI Job / Event / Feedback narrow reads
    -> public field mapping
```

不得调用：

- `AndroidDeviceProvider`
- `DeviceAuthorizationGateway`
- `DeviceCommandService`
- `DeviceBridgeProtocol`
- online Android Session transport
- Reminder Draft handler

设备在线状态、配对状态或 Device Approval 不应影响解释查询。

## 8. Android Companion 是否需要变化

Android Companion 不需要任何变化。

本阶段：

- 不修改 Kotlin/Java 代码。
- 不修改 Android Manifest 或权限。
- 不新增 Android UI、Service、Receiver 或后台任务。
- 不读取 Reminder Draft。
- 不接入 Reminder、Alarm、Calendar、Notification 或其他真实系统 API。

Android Companion 与 P6-9.38 的现有行为保持完全兼容。

## 9. 数据持久化边界

本阶段不新增 migration，也不新增持久化数据。

允许读取：

- `deliveries` 中由 DeliveryStore 暴露并再次白名单映射的字段。
- `delivery_feedback` 中按 Delivery ID 返回的明确反馈类型和时间。
- 现有 AI Job Store 中通过 Delivery `jobId` 精确关联的安全状态字段。
- 现有 EventStore 中通过 Delivery `eventId` 精确关联且已经公共过滤的最小字段。

禁止读取或返回：

- Delivery 正文和内部 worker/retry 字段。
- AI Job prompt、input/output、provider 数据或错误详情。
- Event 未过滤 payload。
- Memory 表及聊天消息正文。

第一版不得通过 SQL join 绕过 Store 的安全边界。应新增小型只读 View/Service，依赖各 Store 的窄查询接口，并在 View 内构造新的公共对象。

如果现有 Store 缺少安全的按 ID 窄查询，应新增只读方法；不得为了本阶段增加表、列、缓存、访问计数或查询历史。

## 10. 测试计划

所有测试使用现有数据库测试夹具和 fake adapter；禁止访问真实模型、真实 Bark、真实 Android 设备或外部服务。

### 10.1 View 单元测试

1. `pending`、`sending`、`sent`、`failed`、`cancelled` 映射到稳定 `summaryCode`。
2. Delivery 输出只包含设计允许字段。
3. AI Job 仅通过 Delivery `jobId` 精确关联。
4. Trigger Event 仅通过 Delivery `eventId` 精确关联。
5. Feedback 仅通过 Delivery ID 精确关联。
6. 缺失关联返回 `available:false` 或 `null`，不抛出内部错误，不推测。
7. Delivery 不存在返回稳定 `DELIVERY_NOT_FOUND`。
8. 输入对象不被修改。

### 10.2 敏感字段测试

1. 响应不含 `text`、prompt、chat、Memory、token、provider response、URL 或 stack。
2. 响应不含 `dedupeKey`、锁、worker、retry 时间和内部 attempt 上限。
3. Event payload 不透传。
4. AI Job input/output 不透传。
5. 错误消息和日志不包含测试注入的敏感标记。

### 10.3 HTTP 测试

1. 合法 Bearer token 的 GET 返回公共 schema。
2. 缺失、错误 token 和未配置 key 被现有认证边界拒绝。
3. 空、超长或不存在的 Delivery ID 被稳定拒绝。
4. POST、PUT、PATCH、DELETE 路由不存在。
5. 查询前后数据库内容完全不变。

### 10.4 MCP 测试

1. `proactive_explanation_get` 可发现，且 input schema 只允许 `deliveryId`。
2. annotations 为完整只读声明。
3. MCP 通过 API client 调用 HTTP，不直接访问 Store 或数据库。
4. MCP 输出再次执行公共字段映射。
5. 不出现 send、retry、cancel、feedback write 或 Device Tool。

### 10.5 副作用与回归测试

1. 不调用模型、AI Adapter、Wake Decision evaluator、Gate 或 Rollout。
2. 不调用 Delivery Worker、Retry Policy 或 Bark Adapter。
3. 不创建 Event，不修改 State、Memory、Delivery、Feedback 或 AI Job。
4. 不调用 Device Command Channel 或 Android transport。
5. 现有 proactive overview、feedback、Tool Runtime 和 Reminder Draft 测试保持通过。
6. 运行 `npm test`。

## 11. 阶段结论

P6-9.13 Proactive Explanation Layer 第一阶段已完成。当前已具备严格只读的数据读取层、认证 GET API 和静态 Tool Registry 定义；它不是新的 Agent 写执行能力。

已验证边界为：无 Approval、无新 Event、无 State/Memory 写入、无 Delivery 逻辑修改、无 Device Command、无 Android 变化、无 migration、无真实外部 API。MCP Server 接入、Companion Center UI 和可靠的逐 Delivery Wake Decision 关联仍未实现；任何发送、重试、取消、设置修改、模型解释或设备能力继续留在本阶段之外。
