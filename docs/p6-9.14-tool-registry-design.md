# P6-9.14 Tool Registry Design

## 1. Tool Registry 目标

Tool Registry 是 Agent Capability Layer 的能力目录，为 Runtime 提供可发现、可验证、可授权的 Tool 定义。

它的目标是：

- 明确 Agent 可以申请哪些能力。
- 为每个 Tool 提供稳定名称、用途、输入 schema、权限等级和执行类型。
- 在执行前为参数校验和 Permission Gate 提供可信元数据。
- 让未知、未注册或版本不兼容的 Tool 默认被拒绝。
- 将模型提出的结构化请求与实际执行模块隔离。
- 为未来本地工具、VPS 工具和手机 Device Bridge 使用统一能力描述。
- 保持 Tool 的注册、授权、执行和审计职责分离。

Tool Registry 不负责：

- 执行 Tool。
- 授予用户权限。
- 调用模型解释参数。
- 保存设备凭据或 API token。
- 修改 Memory、State、关系等级或 AI 人格。
- 将 Tool 自动暴露为 HTTP 或 MCP 能力。

初期建议使用代码内静态 Registry。运行时动态注册、第三方 Tool 安装和远程 Tool Catalog 不属于本阶段范围。

## 2. Tool 定义格式

### 2.1 最小格式

```json
{
  "name": "device.reminder.create",
  "description": "Create a visible reminder after user authorization.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "title": { "type": "string", "minLength": 1, "maxLength": 120 },
      "dueAt": { "type": "string", "format": "date-time" }
    },
    "required": ["title"],
    "additionalProperties": false
  },
  "permissionLevel": "write_low",
  "executionType": "device_bridge"
}
```

基础字段：

- `name`：稳定、唯一、带命名空间的 Tool 名称。
- `description`：面向用户和开发者的简短能力说明，不包含 prompt。
- `inputSchema`：严格输入 schema，默认禁止未知字段。
- `permissionLevel`：Permission Gate 使用的风险和确认等级。
- `executionType`：决定由哪类执行器处理请求。

### 2.2 建议扩展格式

后续实现可在明确需求下增加：

```json
{
  "name": "device.reminder.create",
  "version": "1",
  "description": "Create a visible reminder after user authorization.",
  "inputSchema": {},
  "outputSchema": {},
  "permissionLevel": "write_low",
  "executionType": "device_bridge",
  "supportedPlatforms": ["android", "ios"],
  "requiredSystemPermissions": ["reminders"],
  "confirmationMode": "per_call",
  "idempotent": true,
  "timeoutMs": 15000,
  "retryMode": "never",
  "enabled": false
}
```

扩展字段职责：

- `version`：隔离不兼容 schema 或语义变化。
- `outputSchema`：限制执行器可返回的字段。
- `supportedPlatforms`：明确平台差异，不隐式降级到其他能力。
- `requiredSystemPermissions`：供 Device Bridge 和 Permission Gate 检查。
- `confirmationMode`：定义逐次、会话或限时授权要求。
- `idempotent`：说明相同幂等键能否安全重放。
- `timeoutMs`：限制执行时间。
- `retryMode`：默认不重试；需要重试时必须明确设计。
- `enabled`：Tool 注册与开放状态分离；注册不等于启用。

### 2.3 命名规则

建议格式：

```text
<target>.<resource>.<action>
```

示例：

- `runtime.status.get`
- `device.reminder.create`
- `device.calendar.events_list`
- `relay.device.status_get`

约束：

- 名称必须稳定且不可包含用户、设备或环境标识。
- 读取与写入使用不同 action，不能通过参数切换权限语义。
- 高风险动作不能伪装成 `get`、`preview` 或其他低风险名称。
- 删除、发送、支付等动作必须独立定义，不能作为通用 execute Tool 的自由参数。

### 2.4 Schema 规则

- 根 schema 必须是 object。
- 默认 `additionalProperties:false`。
- 字符串、数组和对象必须有合理长度或数量限制。
- 枚举使用固定白名单。
- 不允许 schema 接受原始脚本、shell command、任意 URL 或任意文件路径，除非未来有独立安全设计。
- 不允许 `includeSecrets`、`raw`、`debug`、`reasoning` 等绕过输出边界的参数。
- schema 校验必须在 Permission Gate 和执行器之前完成。

## 3. Tool Permission 模型

### 3.1 Permission Level

建议采用以下等级：

- `read_public`：读取非敏感、用户可见的运行状态。
- `read_private`：读取联系人、日历、位置或其他受保护数据。
- `write_low`：创建提醒、创建草稿等可见且通常可撤销的操作。
- `write_high`：发送消息、删除数据、发起通话、购买或付款。
- `system_sensitive`：设备管理、无障碍、通知监听、持续后台控制等高权限能力。

默认策略：

- 未注册或未知 permission level：拒绝。
- `read_private`：至少需要明确 scope 和有效授权。
- `write_low`：默认逐次确认；未来只有经评审的 Tool 可采用限时授权。
- `write_high`：必须逐次确认，不能后台静默执行或自动重试。
- `system_sensitive`：默认禁止开放，必须进行独立威胁建模和安全评审。

### 3.2 Permission Gate 输入

Permission Gate 应接收：

- Registry 中的 Tool 定义。
- schema 校验后的参数摘要。
- 请求主体与用户身份。
- 目标设备或执行环境。
- 已存在授权的 tool name、version、scope 和有效期。
- 操作系统权限状态。
- 请求的创建时间、过期时间和幂等键。
- 是否存在本次调用的用户确认。

不允许使用以下信息降低权限要求：

- 用户关系等级。
- 推断情绪。
- AI 人格。
- 模型置信度或 reasoning。
- 历史成功次数。

### 3.3 Gate 结果

```json
{
  "decision": "allow",
  "reasonCode": "PERMISSION_GRANTED",
  "grantId": "opaque-grant-id",
  "expiresAt": "2026-07-20T12:05:00.000Z"
}
```

允许的 decision：

- `allow`
- `require_confirmation`
- `deny`

拒绝、确认超时、授权过期、设备不匹配或系统权限缺失都不能被执行器解释为允许。

### 3.4 授权范围

授权必须绑定：

- 用户。
- Tool name 和 version。
- 目标设备或执行环境。
- 资源和参数 scope。
- 有效期。

例如，允许 `device.reminder.create` 不代表允许读取全部提醒；允许读取一个日历不代表允许修改或删除日历事件。

## 4. Tool 调用生命周期

### 4.1 生命周期

```text
requested
  -> validated
  -> permission_required -> denied
                         -> expired
                         -> approved
  -> dispatched
  -> succeeded | failed | expired | unknown
```

建议流程：

1. Agent 输出结构化 Tool request。
2. Runtime 验证 tool name、version、输入 schema、请求大小和有效期。
3. Registry 返回不可变 Tool 定义；未注册 Tool 立即拒绝。
4. Permission Gate 返回 allow、require confirmation 或 deny。
5. 需要确认时，Runtime 展示具体动作、目标和数据范围。
6. 获得授权后，Dispatcher 选择与 `executionType` 对应的执行器。
7. 执行器再次检查 request ID、幂等键、过期时间和目标范围。
8. 执行结果经过 output schema 与敏感字段过滤。
9. Runtime 通过 EventStore 记录最小化结果事实。
10. Agent 只能接收过滤后的结构化结果。

### 4.2 请求信封草案

```json
{
  "requestId": "opaque-request-id",
  "toolName": "device.reminder.create",
  "toolVersion": "1",
  "arguments": {},
  "target": {
    "type": "device",
    "id": "opaque-device-id"
  },
  "idempotencyKey": "opaque-idempotency-key",
  "createdAt": "2026-07-20T12:00:00.000Z",
  "expiresAt": "2026-07-20T12:05:00.000Z"
}
```

### 4.3 幂等与重试

- 每次请求拥有唯一 `requestId`。
- 支持幂等的 Tool 必须提供稳定 `idempotencyKey`。
- 相同请求不得产生重复外部副作用。
- 默认不自动重试写 Tool。
- 网络状态不明时返回 `unknown`，不能假定失败并再次执行高风险操作。
- Retry 策略属于具体 Tool 定义，不得由模型临时决定。

### 4.4 取消与过期

- 未执行请求可以取消。
- 已开始且平台不支持取消时，必须明确返回不可取消状态。
- 到达 `expiresAt` 后，Gate、Dispatcher 和执行器都必须拒绝执行。
- 用户撤销授权后，所有未执行请求立即失效。

## 5. Tool 执行结果如何产生 Event

### 5.1 原则

Tool 的重要生命周期事实必须通过 `EventStore` 记录。业务模块不得直接写 `events` 表。

建议未来独立评审以下 Event 类型：

- `tool.requested`
- `tool.permission_required`
- `tool.permission_granted`
- `tool.permission_denied`
- `tool.dispatched`
- `tool.succeeded`
- `tool.failed`
- `tool.expired`

本设计不新增 Event 定义，也不修改数据库。

### 5.2 最小 Event payload

```json
{
  "requestId": "opaque-request-id",
  "toolName": "device.reminder.create",
  "toolVersion": "1",
  "executionType": "device_bridge",
  "targetId": "opaque-device-id",
  "reasonCode": "TOOL_SUCCEEDED"
}
```

按 Event 类型可增加安全字段：

- `permissionLevel`
- `grantId`
- `resultCode`
- `durationMs`

禁止写入 Event：

- Tool 原始参数全文。
- 联系人、位置、日历正文、文件内容等设备数据。
- chat history、Memory content、prompt 或 model reasoning。
- API token、Bearer token、设备密钥或签名材料。
- provider response、错误 stack 或原生系统错误全文。

### 5.3 Event 写入时机

- 请求通过基础校验后记录 `tool.requested`。
- Gate 需要确认、允许或拒绝时记录对应权限事实。
- Dispatcher 接受执行后记录 `tool.dispatched`。
- 执行器返回确定结果后记录 `tool.succeeded` 或 `tool.failed`。
- 到期未执行时记录 `tool.expired`。

Event 记录失败不能被伪装成 Tool 成功。对于高风险 Tool，未来实现应明确“外部副作用成功但 Event 写入失败”的恢复和对账策略。

### 5.4 State 边界

Tool Event 不应默认投影到 Companion State。只有未来明确批准的规则化状态才能加入 State Projector。Tool 成功不得自动创建 Memory、改变关系等级或修改 AI 人格。

## 6. 与 MCP 的区别

Tool Registry 和 MCP 解决不同问题：

| 维度 | Tool Registry | MCP |
| --- | --- | --- |
| 角色 | Runtime 内部能力目录和权限元数据 | 向 MCP client 暴露工具或资源的协议层 |
| 是否执行 | 不执行，由 Dispatcher/Executor 执行 | MCP handler 可调用后端服务 |
| 权限依据 | Permission Gate、用户 grant、设备权限 | MCP server 配置、认证和 tool annotations |
| 能力范围 | 可描述本地、设备、VPS 和未来外部能力 | 当前项目仅暴露只读 Memory/State/Relationship/Proactive 查询 |
| 默认策略 | 未注册、未授权即拒绝 | 当前 MCP 全部只读 |
| 用户确认 | 可要求逐次设备或 Runtime 确认 | MCP annotations 本身不等于用户授权 |
| 审计 | 重要执行事实进入 EventStore | 只读查询通常不创建业务 Event |

边界要求：

- Registry 中存在 Tool 不代表必须暴露为 MCP Tool。
- MCP 发现 Tool 不代表获得设备权限。
- MCP annotations 不能替代 Permission Gate。
- 当前 MCP 只读权限模型保持不变。
- 未来若将 Agent Tool 暴露给 MCP，必须作为独立任务明确授权，并同时经过 MCP 认证与 Permission Gate。
- 不能通过 MCP 增加通用 `tool_execute` 来绕过逐个 Tool 的 schema 和权限定义。

## 7. 手机 Device Bridge 如何作为未来 Tool 接入

### 7.1 接入模型

Device Bridge 是 `executionType: device_bridge` 的执行器，不是 Registry 本身。

```text
Tool Registry definition
        |
Capability Request Validator
        |
Permission Gate
        |
Execution Dispatcher
        |
VPS Relay
        |
Mobile Device Bridge
        |
Android/iOS official API
```

### 7.2 Tool 与平台适配

统一 Tool 可以对应平台实现：

```text
device.reminder.create
  -> AndroidReminderBridge
  -> IOSReminderBridge
```

Registry 通过 `supportedPlatforms` 和 `requiredSystemPermissions` 描述差异。平台不支持时返回 `PLATFORM_UNSUPPORTED`，不能用私有 API、无障碍点击或权限绕过模拟实现。

### 7.3 Device Bridge 执行前复核

移动端必须再次验证：

- Runtime 签名。
- request ID 和幂等键。
- tool name 与 version。
- 请求是否过期。
- 目标 device ID。
- 本地系统权限。
- 本地授权或逐次用户确认。

VPS Permission Gate 已允许，不代表设备端可以跳过系统权限或本地确认。

### 7.4 Android 考量

- 使用官方 Intent、WorkManager、Foreground Service 和运行时权限。
- 高权限的 Accessibility、Device Admin、Notification Listener 不作为默认能力。
- 需要前台或常驻通知时必须对用户可见。
- OEM 后台限制或锁屏阻止执行时安全失败。

### 7.5 iOS 考量

- 使用 App Intents、Shortcuts、EventKit、UserNotifications 等公开能力。
- 接受后台执行时间、Push 唤醒和跨应用控制限制。
- 需要前台或系统确认时返回 `USER_INTERACTION_REQUIRED`。
- 不使用私有 API，不追求与 Android 强制功能一致。

### 7.6 初期接入建议

首个真实 Device Tool 应选择低风险、用户可见、易撤销能力，例如创建提醒草稿或打开预填充系统界面。

在真实设备接入前，必须先完成：

- 静态 Registry。
- Permission Gate。
- fake Device Bridge。
- 幂等、超时、取消和敏感字段测试。
- 配对、设备撤销和密钥管理设计。
- VPS Relay threat model。

本阶段不接入真实设备。

## 8. 安全限制

### 8.1 默认拒绝

- 未注册 Tool 拒绝。
- disabled Tool 拒绝。
- schema 不匹配拒绝。
- permission level 未知拒绝。
- 授权缺失、过期或 scope 不匹配拒绝。
- 设备离线、身份不匹配或系统权限缺失时不执行。
- Registry、Gate 或执行器状态不确定时拒绝或返回 unknown，不默认允许。

### 8.2 明确禁止

- 默认完全控制手机。
- 绕过 Android、iOS 或其他系统权限。
- 隐藏执行行为、伪装确认或后台静默执行高风险操作。
- 允许模型注册、启用、修改或删除 Tool。
- 使用通用 shell、任意脚本、任意 URL 或任意文件路径作为初期 Tool。
- 模型输出直接触发执行器。
- 将 read 授权扩大为 write，或将一个设备的授权复用于另一设备。
- 自动修改 Behavior Policy、Memory、State、关系等级或 AI 人格。
- 自动将 Tool 暴露为 HTTP 或 MCP 写接口。

### 8.3 数据与日志边界

禁止在日志、Event 或公共响应中记录：

- API token、Bearer token、设备密钥或签名材料。
- prompt、chat 全文、Memory content、model reasoning。
- provider response、错误 stack。
- Tool 原始敏感参数和完整设备内容。

日志只记录安全的 request ID、tool name、状态和白名单 reason code。

### 8.4 用户控制

- 用户必须能查看已注册且对其开放的 Tool。
- 用户必须能看到请求内容、目标、权限和执行结果。
- 用户可拒绝、撤销 grant、停用 Tool 或断开设备。
- 拒绝、取消和确认超时均不能触发执行。
- 高风险操作必须逐次确认且不得自动重试。

### 8.5 当前阶段边界

P6-9.14 当前仅完成 Tool Registry 设计。未实现 Registry、Permission Gate、Dispatcher、Event、API、MCP、Device Bridge 或 VPS Relay；未新增 migration，也未接入 Android、iOS 或任何真实设备。
