# P6-9.26 Android Device Provider Design

## 1. Android Provider 架构

### 1.1 目标

Android Device Provider 是 Android 设备能力接入 Agent Capability Layer 的平台适配边界。它负责声明 Android 上可用的 Tool，并将已经通过 Registry、Policy、Approval 和 Execution Gateway 的调用转交给受控 Device Bridge。

截至 P6-9.37，Android Device Tool Runtime Integration 已完成基础闭环。当前实现支持：

- `android.device.status_get` / `device.status_get`。
- Android Companion pairing。
- Android Session 建立、heartbeat、断开与过期失效。
- Gateway 与 Android Companion 之间的 Device Command Channel。

Reminder、通知、App 控制、Accessibility、ADB 和其他设备能力仍属于未来阶段，不因基础闭环完成而自动开放。

核心原则：

- Android Provider 只是 Tool Provider 的一种实现，不是独立权限入口。
- 模型不能直接调用 Android API、Provider 或 Device Bridge。
- Provider 不能自行注册未批准 Tool，也不能动态扩大 Tool schema。
- 所有写操作必须对用户可见，并遵守 Android 系统权限。
- Android 平台能力不足、权限缺失或状态不确定时安全失败。
- Provider 返回的原始结果必须继续经过 Result Normalizer 和 Context Bridge。

### 1.2 建议组件

```text
Agent structured request
        |
        v
Tool Registry
        |
        v
Capability Policy
        |
        v
Approval Flow (when required)
        |
        v
Execution Gateway
        |
        v
Tool Provider Registry
        |
        v
Android Device Provider
        |
        v
VPS Relay / authenticated transport
        |
        v
Android Device Bridge
        |
        v
Android public API / visible system UI
        |
        v
Provider result
        |
        v
Result Normalizer -> Context Bridge
```

### 1.3 Android Provider 职责

Android Provider 实现现有 Provider 接口：

```text
name
getMetadata()
listTools()
execute(toolName, input)
```

允许职责：

- 返回 Provider 版本、平台和在线能力等安全 metadata。
- 列出已经在 Tool Registry 中批准的 Android Tool。
- 校验 toolName 是否属于该 Provider。
- 将已授权请求封装为 Device Bridge request。
- 等待受限、结构化的执行结果或稳定 error code。

禁止职责：

- 自行决定 permission level 或 risk level。
- 创建或批准 Approval。
- 绕过 Execution Gateway 直接接受 Agent 请求。
- 将 Android 原始响应直接交给 Agent Context。
- 写 Memory、State 或直接写 `events` 表。
- 读取未包含在 Tool schema 和用户授权 scope 中的设备数据。

### 1.4 Provider metadata 规划

当前 P6-9.37 Provider 仅公开 `device.status_get` 能力。以下 metadata 结构及其他 capability 是未来演进参考，不表示已经实现：

```json
{
  "name": "android_device",
  "platform": "android",
  "version": "1",
  "bridgeProtocolVersion": "1",
  "status": "online",
  "capabilities": ["reminder_draft", "notification_preview"]
}
```

公开 metadata 不包含：

- 设备 token。
- 推送 token。
- 公钥或签名材料。
- Android ID、IMEI、序列号等硬件标识。
- 已安装应用完整列表。
- 联系人、通知或文件内容。
- 内部网络地址和调试信息。

## 2. Device Bridge 与 Tool Provider 边界

### 2.1 Tool Provider

Tool Provider 位于 VPS Runtime 侧，是平台能力的逻辑适配器：

- 接受 Execution Gateway 已放行的 Tool invocation。
- 选择目标 Android Device Bridge。
- 生成有过期时间和幂等键的传输请求。
- 将 Bridge response 映射为 Provider 结果。
- 不直接操作 Android 系统 API。

### 2.2 Device Bridge

Device Bridge 位于 Android 应用侧，是原生系统 API 的窄包装层：

- 验证 Runtime 签名、device ID、request ID、tool name/version 和 expiresAt。
- 检查 Android 系统权限与设备当前状态。
- 在需要时展示本地确认、Activity 或系统 UI。
- 使用 Android 官方公开 API 执行单一、已注册能力。
- 返回安全状态、稳定 result code 和最小结果。

Device Bridge 必须独立复核本地权限。VPS 已通过 Approval 不代表 Android 可以绕过运行时权限、锁屏限制、前台要求或系统确认。

### 2.3 VPS Relay

如果 Provider 与设备通过 VPS Relay 通信，Relay 只负责：

- 认证连接。
- 按 opaque device ID 路由。
- 短期排队。
- acknowledgement、expiry 和幂等状态。
- 在线/离线状态回传。

Relay 不负责：

- 批准 Tool。
- 修改 Tool input。
- 替代本地权限检查。
- 无限期保存请求。
- 保存设备内容或原始结果全文。
- 将一个设备的授权复用于另一个设备。

### 2.4 请求信封草案

```json
{
  "requestId": "opaque-request-id",
  "deviceId": "opaque-device-id",
  "toolName": "android.reminder.draft_create",
  "toolVersion": "1",
  "input": {},
  "idempotencyKey": "opaque-idempotency-key",
  "createdAt": "2026-07-20T12:00:00.000Z",
  "expiresAt": "2026-07-20T12:01:00.000Z",
  "signature": "transport-signature"
}
```

传输中的 input 只能包含该 Tool schema 允许的字段。日志和 Audit Event 不保存 input 全文或 signature。

### 2.5 响应信封草案

```json
{
  "requestId": "opaque-request-id",
  "status": "succeeded",
  "resultCode": "REMINDER_DRAFT_OPENED",
  "result": {},
  "completedAt": "2026-07-20T12:00:05.000Z"
}
```

Provider response 不是最终 Agent Context。`result` 必须经过 Tool Result Normalizer，再由 Tool Context Bridge 根据 classification 决定是否进入当前 context、被拒绝或成为未持久化 candidate。

## 3. 第一批 Android Tool 分类

第一批 Tool 应遵循“低权限、用户可见、易撤销、无静默外部副作用”的原则。以下均为设计候选，不表示已批准实现。

### 3.1 建议首批候选

#### `android.device.status_get`

- 分类：只读设备可用性。
- 建议 risk：low。
- 建议 permission：automatic，但仅返回非敏感状态。
- 输出：online、battery bucket、network availability、app foreground availability 等粗粒度状态。
- 禁止输出：精确位置、SSID、IP、设备唯一标识、已安装应用列表。

#### `android.reminder.draft_create`

- 分类：用户可见的低风险写入草稿。
- 建议 risk：medium。
- 建议 permission：user_confirm。
- 行为：打开预填充提醒界面或在 Companion App 内创建待确认草稿。
- 不允许：后台静默创建后隐藏结果。

#### `android.notification.preview_show`

- 分类：本地可见通知预览。
- 建议 risk：medium。
- 建议 permission：user_confirm。
- 行为：展示由用户确认过的本地通知预览。
- 不允许：读取其他应用通知、伪装系统通知或隐藏来源。

#### `android.clipboard.copy_confirmed`

- 分类：向剪贴板写入用户已确认的短文本。
- 建议 risk：medium。
- 建议 permission：user_confirm。
- 限制：长度和有效期受限，执行前显示内容摘要。
- 风险：剪贴板可能被其他应用读取，因此不允许 secret、token 或 credential。

### 3.2 暂不进入第一批

以下能力默认 high risk 或 system sensitive，不进入第一批：

- 发送短信或即时消息。
- 发起电话。
- 删除文件、照片、联系人或日历事件。
- 读取联系人全集、短信、通知正文、照片库或剪贴板。
- 精确或持续位置跟踪。
- 麦克风、相机或屏幕录制。
- 安装、卸载或控制其他应用。
- Accessibility 自动点击。
- Device Admin、VPN、Notification Listener 或持续后台控制。
- 支付、购买、账户、安全设置或权限设置操作。

这些能力未来若需要，必须逐个创建独立设计和安全评审任务，不能因 Android Provider 存在而自动开放。

## 4. Risk Level 设计

### 4.1 Low

定义：只读取非敏感、粗粒度、低影响状态，不产生设备外部副作用。

示例：

- Companion App 是否在线。
- 粗粒度电量区间。
- 某项已注册能力是否可用。

规则：

- 可被 Capability Policy 判定为 automatic。
- 输出仍需 Result Normalizer。
- 不能包含设备唯一标识、精确位置或私人内容。

### 4.2 Medium

定义：产生用户可见且通常可撤销的本地变化，或读取有限受保护信息。

示例：

- 创建提醒草稿。
- 展示本地通知预览。
- 写入已确认的短剪贴板内容。

规则：

- 必须进入 user_confirm Approval Flow。
- Approval Request 显示 Tool、风险、原因、summary、input hash 和过期时间。
- Android 端仍可要求本地确认或系统 UI。
- 默认不自动重试。

### 4.3 High

定义：可能产生不可逆、跨应用、隐私、账户、财务或人身安全影响。

示例：

- 发送消息、拨打电话。
- 删除数据。
- 精确位置或持续传感器访问。
- 账户、付款和系统管理能力。

规则：

- 当前 Capability Policy 直接 blocked。
- Provider 和 Device Bridge 不得将 high risk Tool 降级为 medium/low。
- 即使 Android 已授予系统权限，也不能绕过 Runtime Policy。

### 4.4 风险不可降级

- Tool Registry/设计评审确定基础风险。
- Capability Policy 可以收紧但不能放宽。
- Provider metadata 和设备端不能自行降低风险。
- 用户关系等级、情绪推断、模型置信度、历史成功次数不能用于降级风险。

## 5. Permission Model

### 5.1 多层权限

Android Tool 必须同时满足：

1. Tool 已在 Registry 注册并启用。
2. Capability Policy 允许 automatic 或要求 user_confirm。
3. 需要时存在匹配 Tool 与 input hash 的有效 Approval。
4. Execution Gateway 放行请求。
5. Provider 识别目标 Tool 和设备。
6. Device Bridge 验证请求签名与过期时间。
7. Android 系统权限已授予。
8. 需要时用户完成本地 UI 确认。

任一层失败都不执行。

### 5.2 Android 系统权限

- 使用 Android 官方 runtime permission。
- 只在用户触发相关能力时请求权限。
- 权限说明必须对应具体 Tool 用途。
- 用户拒绝或系统撤销权限后，返回稳定 error code。
- 不反复弹窗、不引导用户关闭安全保护。
- 不使用 Accessibility 或 Root 绕过权限。

### 5.3 Approval Scope

Approval 必须绑定：

- toolName。
- riskLevel。
- Policy reasonCode。
- inputHash。
- expiresAt。
- 目标 device ID（未来扩展时必须加入安全绑定）。

Approval 不保存 input 全文。不同 Tool、不同参数或过期请求不能复用 Approval。

### 5.4 本地确认

对于 medium risk Tool，Android 界面至少显示：

- 请求来源是 Companion Agent。
- 将执行的具体动作。
- 目标资源和安全摘要。
- 是否会修改设备数据。
- 取消和确认按钮。

确认超时、应用退出、锁屏阻断或用户取消均视为未授权。

## 6. Offline / Error Handling

### 6.1 状态模型

建议 Provider 使用稳定状态：

- `queued`
- `delivered`
- `awaiting_local_confirmation`
- `running`
- `succeeded`
- `failed`
- `expired`
- `cancelled`
- `unknown`

状态仅描述可验证事实，不能推断用户为何离线或拒绝。

### 6.2 离线行为

- 设备离线时，automatic low-risk 请求可在短期限内排队。
- medium-risk 请求的 Approval 和传输请求必须在同一有效期内完成。
- 到达 expiresAt 后，Relay、Provider 和 Device Bridge 都拒绝执行。
- 不无限期保存命令。
- 不自动改发到其他设备。
- 设备恢复在线后只拉取未过期、签名有效的请求。

### 6.3 重试与幂等

- 每次 invocation 使用唯一 requestId。
- 可重试能力必须有 idempotencyKey。
- 写 Tool 默认不自动重试。
- 网络超时且执行结果未知时返回 `unknown`，不能假定失败后再次执行。
- 相同 requestId 在 Android 端不得产生重复副作用。

### 6.4 稳定 error code

建议错误码：

- `ANDROID_DEVICE_OFFLINE`
- `ANDROID_REQUEST_EXPIRED`
- `ANDROID_SIGNATURE_INVALID`
- `ANDROID_TOOL_UNSUPPORTED`
- `ANDROID_SYSTEM_PERMISSION_MISSING`
- `ANDROID_USER_CONFIRMATION_REQUIRED`
- `ANDROID_USER_DENIED`
- `ANDROID_APP_FOREGROUND_REQUIRED`
- `ANDROID_EXECUTION_TIMEOUT`
- `ANDROID_EXECUTION_FAILED`
- `ANDROID_EXECUTION_UNKNOWN`

禁止返回 Android exception stack、原始系统错误全文、网络响应全文或包含用户数据的 message。

### 6.5 取消

- queued 或 awaiting confirmation 的请求可以取消。
- 已调用不可取消的系统 API 后，不得虚假报告取消成功。
- 用户撤销设备或 Tool grant 后，未执行请求立即失效。

## 7. Audit 边界

### 7.1 审计入口

重要 Tool 生命周期事实必须由 Runtime 的 Tool Audit Store 通过 EventStore 记录。Android Provider 和 Device Bridge 不直接写 `events` 表。

现有安全 Tool Event：

- `tool.requested`
- `tool.approved`
- `tool.completed`
- `tool.failed`

未来若增加 delivered、expired、cancelled 等事件，必须单独扩展 Event 定义和测试；本设计不新增 Event。

### 7.2 允许审计字段

- toolName。
- approvalStatus。
- success/failure。
- 白名单 errorCode。
- EventStore 生成的 createdAt。

未来可在单独评审后增加 opaque requestId/deviceId，但不得记录真实设备标识。

### 7.3 禁止审计内容

- Tool input 或 output 全文。
- inputHash 以外可恢复输入的信息；当前公共 Tool Audit API 也不返回 hash。
- 文件、照片、联系人、日历、通知、剪贴板或消息内容。
- API token、Bearer token、push token、设备密钥和签名。
- Android exception、stack、debug dump 和内部网络信息。
- prompt、chat history、Memory content、model reasoning 或 provider response。

### 7.4 Provider 本地日志

Provider 与 Device Bridge 日志仅允许：

- opaque requestId。
- toolName。
- 安全状态。
- 白名单 errorCode。
- 粗粒度耗时。

生产日志不得包含 input、result、Approval summary、系统权限 token 或设备内容。

## 8. 禁止绕过

### 8.1 Policy

- Android Provider 不调用或替代 Capability Policy。
- Provider 不能将 high risk 降级。
- Policy blocked 后不得创建 Device Bridge request。
- Policy 异常必须 fail closed。

### 8.2 Approval

- user_confirm Tool 没有有效 Approval 时不得下发。
- Approval 必须匹配 toolName、inputHash、riskLevel 和有效期。
- Android 系统权限不能替代 Runtime Approval。
- Provider 或设备不能自行生成 approved 状态。

### 8.3 Execution Gateway

- Agent、HTTP、MCP、Provider 和 Relay 都不能直接调用 Device Bridge 执行 Tool。
- Provider 只接受 Execution Gateway 已完成 Registry、Policy、schema 和 Approval 检查的 invocation。
- 不提供通用 `android.execute`、任意 Intent、shell 或脚本 Tool。

### 8.4 Result Normalizer

- Provider 原始结果不能直接返回 Agent。
- 所有结果必须递归过滤敏感键并受 10KB 限制。
- token、secret、password、credential、apiKey、stack、debug 和 internal 字段必须移除。
- Result Normalizer 失败时不返回原始结果作为 fallback。

### 8.5 Context Bridge

- normalized result 仍不能自动进入 Agent Context。
- ephemeral 只进入当前 context。
- sensitive 默认拒绝，等待未来明确的 context approval 设计。
- persistent_candidate 只生成未持久化 candidate，不直接写 Memory。
- Provider 不能修改 classification 或绕过 Context Bridge。

### 8.6 其他明确禁止

- 默认完全控制手机。
- ADB、Root、Accessibility 自动点击或私有 API 绕过。
- 隐藏执行行为或伪装系统 UI。
- 直接写 Memory、State 或 Event 表。
- 自动调用模型解释或改写设备结果。
- 自动接入 MCP 写能力。
- 未经后续明确阶段授权，实现额外 migration、真实设备控制或数据库变更。

## 当前阶段结论

P6-9.26 完成了 Android Device Provider 的架构设计；后续阶段已推进至 P6-9.37，并完成 Android Device Tool Runtime Integration 基础闭环。当前已实现 Android Provider、Android Companion、设备 pairing、长期 Session、Device Command Channel，以及唯一开放的 `android.device.status_get` Tool。

当前不包含 reminder 执行、通知读取、App 控制、Accessibility、ADB、VPS Relay 或其他设备能力。未来阶段仍须逐项设计、授权和测试，并继续遵守 Registry、Policy、Approval、Execution Gateway、Device Protocol、Result Normalizer 和 Context Bridge 的完整调用链。
