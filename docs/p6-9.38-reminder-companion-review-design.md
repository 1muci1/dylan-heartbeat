# P6-9.38 Reminder Draft Companion Review Experience Design

## 1. 背景与目标

P6-9.38 第一阶段已经允许经过逐次 Approval 的 `android.reminder.draft_create` 命令，在 Android Companion 内创建一个待用户检查的草稿。当前 Android 实现仍是原型：草稿仅保存在进程内 handler 中，MainActivity 没有草稿入口、列表或详情。

本阶段只设计 Companion 前台检查体验，使用户能在应用内看见已经创建的 Reminder Draft，理解它尚未成为系统提醒，并可以在本地拒绝不需要的草稿。

本设计不授权代码实现、Android 本地 schema 变更、Gateway migration、新 API 或真实 Reminder 能力。

## 2. 当前 Android ReminderDraftHandler 能力

当前模型：

```kotlin
ReminderDraft(
    draftId: String,
    title: String,
    time: String,
)
```

当前 `InMemoryReminderDraftHandler` 能够：

- 接收已由上游验证的 `title` 和 UTC ISO time。
- 生成不透明随机 `draftId`。
- 将草稿写入当前进程内 `MutableMap`。
- 通过 `get(draftId)` 返回副本。
- 向 Device Command 返回 `{draftId,status:"created"}`。

当前不能：

- 列出全部或待检查草稿。
- 表达 `rejected`、`expired` 或其他生命周期状态。
- 记录创建、拒绝或过期时间。
- 在 MainActivity 中共享同一个 repository 实例。
- 跨进程或 App 重启恢复草稿。
- 按 commandId 去重或回放 receipt。
- 删除、归档或执行系统 Reminder。

MainActivity 当前仅展示 fake pairing 和 fake device status。它创建的 `FakeDeviceTransport` 内部拥有 handler，但 UI 无法读取该 handler，因此不能在现有结构上直接渲染草稿。

## 3. 设计目标

- 用户可以从 Android Companion 前台进入“Reminder 草稿”页面。
- 页面只展示 Companion 本地草稿，不查询 Gateway 的完整 payload。
- 用户能区分“已创建草稿”和“系统提醒已创建”；后者始终不成立。
- 生命周期规则稳定、可测试，不根据用户心理或模型输出推断状态。
- 查看不自动执行任何操作。
- 拒绝只改变 Companion 本地草稿状态，不调用系统 API。
- 过期由本地确定性时间规则产生，不触发 Reminder、Notification 或后台任务。
- 与未来 command receipt 幂等设计兼容，但不在本阶段隐式实现它。

## 4. 草稿数据模型与生命周期

### 4.1 建议公共模型

前台 review repository 至少需要：

```text
draftId
title
time
status
createdAt
decidedAt (nullable)
expiresAt
```

允许状态：

```text
created
rejected
expired
```

这些状态只描述 Companion 应用内草稿，不是 Tool Approval 状态、Device Command 状态或系统 Reminder 状态。

### 4.2 `created`

含义：

- Device Command 已在 Companion 内创建可见草稿。
- 草稿等待用户前台检查。
- 不表示 Alarm、Calendar、Notification 或系统 Reminder 已创建或已安排。

合法转换：

```text
created -> rejected
created -> expired
```

仅打开详情不改变 `created`。本阶段不增加 `reviewed`、`accepted` 或 `scheduled`，避免“看过”被误解为执行授权。

### 4.3 `rejected`

含义：用户在 Companion 前台明确选择“不保留此草稿”。

规则：

- 必须由用户点击明确的二次确认控件产生。
- 只能从 `created` 转换。
- 重复拒绝必须幂等，返回现有 `rejected` 状态。
- 不调用 Gateway、Device Command 或 Android 系统 API。
- 不创建新 Approval、Audit Event、State 或 Memory。
- 不等同于 Tool Approval `rejected`；Tool Approval 发生在创建前，draft rejection 发生在草稿已创建后。

本阶段建议保留最小 tombstone metadata，避免草稿从 UI 消失后无法解释状态；title/time 的清理策略见持久化边界。

### 4.4 `expired`

含义：一个仍为 `created` 的草稿超过本地 review 窗口，或其目标时间已按明确规则失效。

推荐使用固定、可测试的规则：

- `expiresAt` 在创建时由本地常量计算并保存。
- 当页面加载、恢复前台或读取 repository 时，若 `now >= expiresAt`，原子转换为 `expired`。
- 不使用后台 Service、AlarmManager、WorkManager 或 Notification 来推动过期。
- 不因 App 关闭期间未运行而伪造精确的过期执行时刻；下次前台读取时完成确定性转换。
- 已 `rejected` 的草稿不再转换为 `expired`。

具体 review TTL 以及是否以 `min(configured TTL, reminder time)` 为 expiresAt，需要在实现前确定。不得默默修改用户提供的 reminder time。

### 4.5 终态与删除

`rejected` 和 `expired` 是终态：

- 不允许恢复为 `created`。
- 不允许从终态执行或创建系统提醒。
- 如果用户仍需要新的草稿，必须从 Gateway 发起新的 Tool 调用并获得新的 Approval。

物理删除或自动清理不属于本阶段。未来如需 retention cleanup，应单独定义期限、tombstone、用户可见性和 command receipt 关联。

## 5. 页面入口与信息架构

### 5.1 入口

在 MainActivity 的已配对区域增加固定入口：

```text
Reminder 草稿
```

入口显示本地 `created` 数量，不从 Gateway 获取。未配对时可以隐藏入口或显示空状态，但本地已有草稿不能因临时离线而被删除。

### 5.2 草稿列表

默认只展示 `created` 草稿，按 `createdAt` 降序排列。可提供本地“已拒绝/已过期”分组，但不是实现第一阶段的必需项。

列表允许展示：

- title。
- 本地格式化后的 time。
- 固定状态文案“待检查”。
- createdAt。
- draftId 的缩略标识（可选，仅用于排障；不能构造外部链接）。

列表不自动刷新、不轮询 Gateway。页面恢复前台时可重新读取本地 repository，并应用过期规则。

### 5.3 草稿详情

详情页或对话框允许展示：

- title。
- time。
- status 及明确解释。
- createdAt。
- expiresAt。
- rejected 时的 decidedAt。

`created` 详情只提供：

- 返回。
- “不保留此草稿”本地拒绝动作，需二次确认。

不提供“确认创建提醒”“保存到系统”“立即执行”等入口。

## 6. UI 展示边界

### 6.1 必须展示的语义

页面顶部必须固定说明：

> 这些内容只是 Companion 应用内草稿，不会创建系统提醒或通知。

状态文案：

| 状态 | 用户文案 | 含义 |
| --- | --- | --- |
| `created` | 待检查 | Companion 内存在草稿，尚未执行 |
| `rejected` | 已拒绝 | 用户明确不保留该本地草稿 |
| `expired` | 已过期 | 草稿超过本地检查窗口，未执行 |

不得使用“已安排”“将提醒”“已保存到系统”“提醒生效”等文案。

### 6.2 禁止展示的数据

Android UI、错误、日志和可访问性描述不得展示：

- Approval ID、input hash 或 Approval 内部 metadata。
- commandId、requestId、sessionId、device secret、pairing token。
- Gateway API/Bearer token 或 Authorization header。
- Device Protocol payload/response 全文。
- prompt、聊天全文、Memory content、模型输出或 reasoning。
- provider response、错误 stack、SQL 或内部路径。
- 任何与当前草稿无关的设备、联系人、Calendar 或 Notification 数据。

title/time 是用户草稿内容，只能在 Companion 本地 review UI 中展示，不上传到 Gateway Audit/Event，不写日志。

### 6.3 错误展示

- repository 不可用：显示“草稿暂时无法加载”，不显示异常详情。
- 草稿不存在：显示“草稿不存在或已清理”。
- 非法状态：安全失败并隐藏动作，不猜测状态。
- 拒绝写入失败：保持原状态，显示“未能更新草稿，请重试”，不得显示 stack。

## 7. 是否需要本地持久化

### 7.1 结论

若目标是可用的前台检查体验，需要 Android 本地持久化。

继续使用 `InMemoryReminderDraftHandler` 只能形成演示：

- App 重启即丢失草稿。
- 收到 Device Command 的 handler 与 MainActivity UI 难以共享可靠状态。
- 无法保存 status、createdAt、expiresAt 或 rejected 决策。
- 无法与未来 command receipt 去重边界协调。

因此实现前应引入一个受限的 `ReminderDraftRepository`，由 Device Command handler 和 UI 共享。具体选择 Room、SQLite 或受限文件存储需在实现任务中明确。

### 7.2 本地数据边界

允许在 Companion 私有应用存储中保存：

- draftId。
- title。
- UTC time。
- `created|rejected|expired`。
- createdAt、decidedAt、expiresAt。

禁止保存：

- Approval ID、Gateway token、pairing token、sessionId。
- Device request/response 全文。
- prompt、聊天或 Memory。
- 系统 Calendar/Alarm/Notification 标识。

`android:allowBackup="false"` 必须保持，草稿不得进入系统备份。不得使用外部存储或共享 provider。

Android 本地 schema 变化不等同于 Gateway migration，但仍需要明确版本、旧版本初始化、升级和失败恢复测试。本设计阶段不新增任何 schema 或 migration。

## 8. 重启行为

### 8.1 推荐行为

App 重启后：

1. repository 从应用私有存储恢复草稿。
2. 对 `created` 草稿应用确定性过期规则。
3. `rejected`、`expired` 保持终态。
4. UI 显示恢复后的本地状态。
5. 不联系 Gateway，不重发 Device Command，不重新创建 draft。

设备离线、Gateway 不可用或 pairing session 失效不影响已经保存的本地草稿可见性。

### 8.2 与幂等设计的关系

前台 review repository 与 command receipt index 可以共享同一事务数据库，但必须保持逻辑分层：

- Draft 表保存本地用户可见内容和状态。
- Receipt 表保存 commandId 到 draftId 的最小去重关联，不保存 title/time 副本。

若两者不能在创建时原子提交，必须在 Reminder idempotency 实现设计中说明崩溃窗口。前台 review 设计本身不能替代 command 幂等。

## 9. Gateway 是否参与

### 9.1 创建阶段

Gateway 继续参与现有创建链路：

```text
approved Tool
    -> ToolExecutionGateway
    -> AndroidDeviceProvider
    -> Device Command
    -> Companion ReminderDraftRepository
```

本设计不改变 Tool schema、Approval、Provider、Audit 或创建结果。

### 9.2 前台 review 阶段

Gateway 不参与：

- 列表和详情从 Companion 本地 repository 读取。
- 查看不产生 HTTP/MCP 请求。
- reject/expire 不回传 Gateway。
- 不新增草稿 list/detail/reject API。
- 不写 Gateway Event、State、Memory 或 Audit。

原因：前台 review 是设备本地草稿管理，不应为便利扩展新的远程写能力或上传用户草稿内容。

Gateway 中已完成的 `{draftId,status:"created"}` receipt 只证明创建时成功，不随本地 rejected/expired 改写。若未来需要跨端状态同步，必须作为独立阶段设计隐私、Event 和冲突边界。

## 10. Device Command 是否参与

Device Command 只参与已批准的草稿创建。

以下操作不经过 Device Command：

- 打开草稿列表。
- 查看详情。
- 本地 reject。
- 前台读取时计算 expire。
- 本地状态筛选。

不得新增：

- `reminder.draft_list`
- `reminder.draft_get`
- `reminder.draft_reject`
- `reminder.draft_accept`
- 通用 reminder action

未来 command receipt 查询属于幂等协议问题，不是 review UI 操作；需按独立设计批准。

## 11. 禁止的真实 Reminder 能力

本阶段禁止使用或接入：

- Android Reminder API 或任意第三方 Reminder provider。
- `AlarmManager`。
- `CalendarContract`。
- `NotificationManager` 或 Notification Channel。
- WorkManager/JobScheduler 定时执行。
- 后台 Service、前台 Service 或开机广播。
- Intent 启动 Calendar/Alarm/Reminder 应用。
- Accessibility、ADB、Root 或界面自动操作。

Manifest 权限必须继续只有：

```text
android.permission.INTERNET
```

不增加通知、日历、精确闹钟、后台运行、存储或其他权限。

## 12. 安全与状态约束

- 不自动接受、执行或安排任何草稿。
- 不因为用户打开详情而改变状态。
- reject 必须由用户在 Companion 前台明确触发并确认。
- expire 只能由固定时间规则产生，不由模型或 Gateway 推断。
- 不绕过创建阶段 Approval。
- 不允许模型输出直接改变草稿状态。
- 不写 Memory、Companion State 或关系等级。
- 不把草稿内容记录到 Event、Audit 或日志。
- UI 和 repository 不暴露任意 action/payload 接口。
- 所有动态文本使用 Android TextView 等安全文本属性，不解析 HTML/WebView 内容。

## 13. 实现前测试计划

测试使用 fake clock、临时本地 store、fake handler 和 fake Device transport；禁止真实 Gateway、模型、Bark、Calendar、Alarm、Notification 或外部服务。

### 13.1 Repository 与生命周期

1. create 保存规范的 draftId/title/time/status/时间 metadata。
2. list 默认只返回 created，顺序稳定。
3. get 返回副本或不可变模型，调用方不能修改 store。
4. created 可以原子转换为 rejected。
5. 重复 reject 幂等，不更新第二次 decidedAt。
6. created 到期后在读取时转换为 expired。
7. rejected 不再转换为 expired。
8. rejected/expired 不能恢复 created。
9. 非法或未知状态安全失败。

### 13.2 重启与持久化

1. 关闭并重建 repository 后 created 草稿仍存在。
2. App 关闭期间到期的草稿在下一次读取时变为 expired。
3. rejected/expired 在重启后保持终态。
4. 重启不调用 Gateway 或 Device Command。
5. 新数据库初始化、旧 schema 升级和重复本地 migration 幂等。
6. `allowBackup=false` 保持不变，不使用外部存储。

### 13.3 UI

1. 已配对前台存在明确的 Reminder 草稿入口。
2. 空列表、created、rejected、expired 状态文案正确。
3. 页面固定显示“仅为应用内草稿”的说明。
4. title/time 仅在本地 UI 显示，不进入日志或可共享 Intent。
5. 打开列表或详情不改变草稿状态。
6. reject 必须二次确认，取消确认不改变状态。
7. repository 错误不显示 stack 或内部异常。
8. 小屏、旋转、Activity 重建和无障碍标签可用。

### 13.4 Gateway / Device 边界

1. 创建仍要求 approved Approval、paired/online device 和固定 action。
2. list/detail/reject/expire 不调用 Gateway、HTTP、MCP 或 Device Command。
3. 不新增 Device action。
4. Gateway 不保存或接收本地 review 状态和 title/time。
5. 本地 review 不重复创建 draft，不改变创建 receipt。

### 13.5 禁止能力与回归

1. 源码不引用 AlarmManager、CalendarContract、NotificationManager、WorkManager、JobScheduler 或 Reminder provider。
2. Manifest 仍只有 INTERNET 权限。
3. 不启动 Service、Intent 或广播执行提醒。
4. Android JVM 单元测试通过。
5. Android `assembleDebug` 通过（构建环境可用时）。
6. Node `npm test` 全量通过。
7. `git diff --check` 通过。

## 14. 实现前结论

当前 `InMemoryReminderDraftHandler` 足以证明 Device Command 能创建最小草稿，但不足以支持可靠的 Companion 前台检查体验。实现该体验需要共享的本地 repository、显式草稿生命周期和跨 Activity/App 重启恢复策略。

推荐边界是：Gateway 和 Device Command 只负责已有 Approval 后的创建；列表、详情、reject 和 expire 完全留在 Android Companion 本地。整个阶段继续保持“应用内草稿”语义，不接入任何真实 Reminder、Calendar、Alarm 或 Notification 能力。

由于本地存储方案、TTL、Android schema 和与 command receipt 的事务关系尚需明确批准，该方向仍为 `NOT_READY`。在这些边界确定前，不进入实现、不新增 migration，也不修改现有业务代码。
