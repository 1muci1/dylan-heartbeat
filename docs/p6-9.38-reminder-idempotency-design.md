# P6-9.38 Reminder Draft Approval / Execution Idempotency Design

## 1. 背景与设计范围

P6-9.38 第一阶段已经通过现有 Tool Runtime 和 Android Device Command Channel 实现：在逐次用户 Approval 后，于 Android Companion 进程内创建一个待检查的 Reminder Draft。

当前实现能够阻止同一 `approvalId` 在同一个 `ToolExecutionGateway` 实例内被顺序重复使用，但不提供跨重启、多实例、并发或网络结果不确定场景下的强幂等保证。本设计定义后续持久化和协议边界，不授权代码实现、migration 或真实 Reminder 能力。

设计仅适用于：

```text
android.reminder.draft_create
```

它不把 Approval 扩展为长期设备授权，也不改变其他 Tool 的权限模型。

## 2. 当前执行链分析

### 2.1 Approval

当前 `ToolApprovalStore`：

- 使用进程内 `Map` 保存 Approval。
- 状态只有 `pending`、`approved`、`rejected`、`expired`。
- 保存 `toolName`、canonical `inputHash`、安全摘要和时间信息。
- `pending` 与 `approved` 到期时会在读取中变为 `expired`。
- 不存在持久化的 `consumed` 状态，也不关联 execution、command 或 result。

`ToolExecutionGateway` 对规范请求计算 canonical input hash。执行请求必须同时匹配 `approvalId`、Tool name 和 input hash；否则在进入 Provider 前拒绝。

### 2.2 ToolExecutionGateway

对于 `user_confirm` Tool，当前顺序为：

```text
load approved Approval
    -> check process-local usedApprovalIds
    -> audit tool.approved
    -> add approvalId to usedApprovalIds
    -> Provider.execute
    -> audit tool.completed / tool.failed
```

`usedApprovalIds` 是进程内 `Set`。加入发生在 Provider 调用前：

- 同一进程中的顺序重复调用会返回 `TOOL_APPROVAL_ALREADY_USED`。
- Provider 失败后，该 Approval 在当前进程内仍被视为已使用。
- 没有保存成功结果，重复调用不能回放既有 `draftId`。
- claim、Provider 调用和 Audit Event 之间没有数据库事务。

### 2.3 Device Command

`AndroidDeviceProvider` 在重新验证和规范化 title/time 后执行：

```text
DeviceAuthorizationGateway.authorize
    -> DeviceCommandService.execute
```

当前 `DeviceCommandService`：

- 每次调用生成新的 `commandId`。
- `DeviceBridgeProtocol` 每次调用再生成新的 `requestId`。
- `DeviceCommandStore` 是进程内 `Map`。
- Command 状态为 `created -> sent -> completed|failed`。
- Store 不保存 payload 或 response，这是正确的敏感数据边界。
- timeout 会直接把 Command 标记为 `failed`，但无法证明设备是否已经完成操作。
- 没有“使用同一 commandId 重发并回放结果”的接口或协议。

因此当前 `failed` 同时混合了确定失败与结果未知两种语义。

### 2.4 Android ReminderDraftHandler

Android 当前使用 `InMemoryReminderDraftHandler`：

- 每次 `create(title, time)` 生成新的随机 `draftId`。
- 草稿只保存在进程内 `MutableMap`。
- handler 不接收 Approval ID、command ID 或幂等键。
- 同一 payload 被调用两次会创建两个草稿。
- App 重启后草稿和去重信息都会丢失。

`DeviceCommandClient` 验证 `commandId`、deviceId、action 和 payload，但没有保存已处理 command 的 receipt，也没有重复 command 回放逻辑。

## 3. 当前幂等问题

### 3.1 进程内 `usedApprovalIds`

它只能保护一个 Gateway 对象生命周期内的顺序重复请求，不能作为业务事实来源。它既不能跨进程共享，也不能恢复已完成结果。

### 3.2 Gateway 重启

重启后 Approval Store、`usedApprovalIds` 和 DeviceCommandStore 全部丢失。当前 Approval 本身通常无法继续使用；如果上层重建或重复发起相同意图，系统无法判断旧请求是否已到达设备。

### 3.3 多实例

两个 Gateway 实例各自拥有独立 Map/Set。它们可能同时读取同一 approved Approval，并各自创建 Device Command。仅靠 Event/Audit 的先查后写不能避免竞态。

### 3.4 并发执行

即使在单进程内，两个异步调用也可能都在 `usedApprovalIds` 检查前后竞争。JavaScript 同步段目前降低了单实例重复进入概率，但该事实不是跨实例原子锁，也没有数据库唯一约束作为最终防线。

### 3.5 网络超时

超时存在至少三种不可区分情况：

1. 请求未到设备。
2. 设备收到请求但尚未创建草稿。
3. 设备已创建草稿，但 acknowledgement 丢失。

将三者统一标为 `failed` 后重新生成 command 会在第 3 种情况下创建重复草稿。

### 3.6 Device Command 重试

当前每次 execute 都生成新的 commandId/requestId，Android handler 也不按 command 去重。因此“重试”实际是新的写操作，不是安全的传输重放。

## 4. 设计目标与语义

### 4.1 核心目标

- 同一 Approval 最多产生一个逻辑 Reminder Draft execution。
- 同一逻辑 execution 的传输重试复用同一个稳定 command ID。
- Android 对重复 command 返回同一个 receipt，不重复创建草稿。
- 成功结果可以安全回放，重复调用不再次访问设备。
- 不确定结果不会被错误标为确定失败，也不会自动创建新 command。
- Approval、execution、command 和 draft receipt 可以使用非敏感标识精确关联。

这里的目标是“effectively once”：Gateway 通过原子 claim 保证一个逻辑 execution，Android 通过持久化 command receipt 保证重复传输不重复产生 draft。仅凭网络协议无法获得没有设备侧去重的 exactly-once 副作用。

### 4.2 同一 Approval 的重复调用

推荐行为：

- execution `completed`：返回已保存的最小 receipt，不再次发送 Device Command。
- execution `claimed`/`dispatched`：返回稳定的 `TOOL_EXECUTION_IN_PROGRESS`，不并发发送。
- execution `outcome_unknown`：返回稳定的 `TOOL_EXECUTION_OUTCOME_UNKNOWN`，仅允许状态确认，不创建新 command。
- execution `retryable_failed`：在 Approval 仍有效且 retry policy 允许时，可以恢复同一 execution，并复用同一 command ID。
- execution `terminal_failed`：不允许复用 Approval；如用户仍希望创建草稿，必须发起新的 Approval。

重复调用不应只返回 `TOOL_APPROVAL_ALREADY_USED`；当存在已完成 receipt 时，应安全回放原结果。

### 4.3 失败后是否允许重试

按是否可能产生设备副作用分类：

| 失败位置 | 结果分类 | 同一 Approval 行为 |
| --- | --- | --- |
| claim 前校验失败、Approval 不匹配/过期 | 未执行 | 不允许执行；需要有效 Approval |
| Device 授权、配对、在线检查失败，且未 dispatch | retryable 或 terminal，按稳定错误策略 | 可在原 Approval 有效期内恢复同一 execution；不得生成第二个 execution |
| command 已发送，收到明确“未执行”的协议拒绝 | terminal_failed | 不自动重试；新意图需要新 Approval |
| command 已发送后 timeout、断线、响应丢失/非法 | outcome_unknown | 不创建新 command；只允许使用同一 command ID 查询或重放 |
| Android 返回成功 receipt | completed | 回放相同 receipt |

任何自动传输重试都必须满足：同一 execution、同一 command ID、Android 已实现持久化去重和 receipt 回放。在此前不得自动重试 Reminder Draft command。

### 4.4 执行结果确认

成功只有在收到并验证以下最小 acknowledgement 后成立：

```json
{
  "commandId": "opaque-command-id",
  "status": "completed",
  "receipt": {
    "draftId": "opaque-draft-id",
    "status": "created"
  }
}
```

确认条件：

- commandId 与该 execution 持久化的 commandId 完全一致。
- Device session 对应已批准的目标 device。
- action 固定为 `reminder.draft_create`。
- receipt 通过现有严格输出 schema。
- 持久化 execution 从非终态原子转换到 `completed`。

响应丢失不能推断为失败；必须保持 `outcome_unknown`，等待相同 command 的 receipt 查询或重放。

### 4.5 Draft ID / receipt 关联

持久化关联链建议为：

```text
approvalId (unique)
    -> executionId (unique, opaque)
    -> commandId (unique, stable)
    -> draftId (nullable until confirmed, opaque)
```

允许保存 `draftId`，因为它是不透明 receipt 标识，且回放已完成结果需要它。禁止从 title/time 派生 draftId、commandId 或 executionId。

## 5. 持久化边界

### 5.1 是否需要 migration

若要实现跨重启、多实例和并发的强幂等，Gateway 需要 migration。当前全部相关 Store 均为进程内结构，不能满足目标。

本设计阶段不新增 migration。进入实现前必须单独批准 schema、升级/回滚策略以及新库初始化、旧库升级和重复 migration 幂等测试。

### 5.2 是否需要新表

推荐至少新增专用 execution receipt 表，而不是扩展 Event 表：

```text
tool_execution_receipts
```

最小字段建议：

- `execution_id`：opaque primary key。
- `approval_id`：opaque，唯一约束，保证一个 Approval 只有一个逻辑 execution。
- `tool_name`：必须为 `android.reminder.draft_create` 或受限 Tool name。
- `input_hash`：与 Approval canonical hash 一致。
- `device_id`：已配对设备的非密钥标识。
- `command_id`：opaque，唯一且整个 execution 生命周期稳定。
- `status`：`claimed|dispatched|outcome_unknown|retryable_failed|terminal_failed|completed`。
- `draft_id`：仅 completed 后保存的 opaque receipt ID，可为空。
- `result_status`：仅允许 `created`，可为空。
- `error_code`：仅稳定白名单 code，可为空。
- `created_at`、`updated_at`、`completed_at`。
- 可选 `version` 或 lease metadata，用于 compare-and-swap；不得把 lease 当成重新执行未知副作用的许可。

必须由数据库事务和 `UNIQUE(approval_id)` 完成原子 claim。应用层先查再插不是多实例幂等保证。

Approval 本身也需要持久化，才能可靠支撑跨重启的 approved/expired 判断。可选择：

1. 新增独立 `tool_approvals` 表，并保持 Approval 与 execution 分离；推荐。
2. 将 Approval 最小字段与 execution 合并；会耦合生命周期，不推荐。

Android 若要跨 App 重启去重，也需要受限的本地 command receipt 持久化。其 schema、加密、清理和版本升级必须在实现阶段明确；不能继续只依赖 `InMemoryReminderDraftHandler`。

### 5.3 是否可以只使用现有 Event/Audit

不可以。

现有 Event/Audit 适合记录最小业务事实，但不适合作为幂等锁或结果存储：

- 当前 Audit payload 不保存 approvalId、executionId、commandId 或 draftId。
- Event append 与 Provider dispatch 之间没有原子事务。
- 多实例“查询是否已有 Event，再执行”存在竞态。
- `tool.completed` 没有可回放的 receipt。

Event/Audit 应继续记录安全的生命周期事实，但执行真相由专用 execution receipt Store 提供。所有 Audit Event 仍必须通过 `ToolAuditStore -> EventStore`，禁止业务模块直接写 events 表。

### 5.4 禁止持久化的数据

Gateway、Event/Audit、Device Command metadata 和 Android receipt index 均不得保存：

- reminder title 全文或片段。
- time 原始输入；如无业务必要，规范化时间也不进入 execution receipt。
- 完整 Tool input 或 Device Protocol payload。
- Device response 全文。
- prompt、聊天全文、Memory content、模型输出或 reasoning。
- API/Bearer/pairing token、sessionId、设备密钥或认证 header。
- provider response、错误 message、URL、SQL 或 stack。

允许保存的关联值仅限 opaque ID、input hash、固定 Tool/action、稳定状态、稳定 error code 和时间 metadata。

## 6. Approval 生命周期

### 6.1 是否扩展 Approval 状态

推荐保持现有用户决策状态：

```text
pending -> approved | rejected | expired
```

不建议直接把 `consumed`、`failed` 加入 Approval 状态，因为它们描述执行结果，而不是用户是否授权。混合两类状态会造成：

- approved 后执行中无法准确表达。
- timeout 时无法区分失败与未知结果。
- Approval 审计与 execution 重试策略耦合。

推荐通过关联 execution 派生展示状态：

- `approved + claimed/dispatched`：已批准，执行中。
- `approved + completed`：已批准，已消费。
- `approved + retryable_failed`：已批准，执行前失败。
- `approved + outcome_unknown`：已批准，结果待确认。
- `approved + terminal_failed`：已批准，执行失败且已消费。

因此 `consumed` 是 execution 存在且进入不可创建第二 execution 的事实，不是新的可转换 Approval 状态。

### 6.2 Expiry 规则

- 只有在 Approval 有效且为 approved 时才能首次原子 claim execution。
- execution 已成功 claim 后，Approval 随后过期不能取消已经 dispatch 的设备操作。
- Approval 过期后不能创建新的 execution。
- `retryable_failed` 是否可恢复必须同时满足 execution policy 和 Approval 尚未过期。
- `outcome_unknown` 的结果确认不受 Approval 过期阻断，因为它不是新执行。

### 6.3 原子消费

推荐事务：

1. 读取并锁定 Approval，验证 approved、未过期、Tool/input hash 匹配。
2. `INSERT tool_execution_receipts`，由 `UNIQUE(approval_id)` 竞争一个 winner。
3. 提交事务后，只有 winner 可以进入 Provider。
4. loser 读取既有 execution 状态，返回 in-progress、unknown、terminal error 或 completed receipt。

不得在数据库事务内等待设备网络调用。

## 7. Device Command 边界

### 7.1 Command ID

- commandId 在 execution claim 时生成一次并持久化。
- Provider、DeviceCommandService、协议和 Android client 必须使用同一个 commandId。
- transport attempt 可以有独立 requestId，但 requestId 只做单次响应相关；不能作为副作用幂等键。
- 同一 execution 的任何重发不得生成新 commandId。
- 新 Approval 必须生成新的 executionId 和 commandId。

### 7.2 Retry

Device Command retry 仅指传输层重放，不是再次执行业务命令：

- 只能重放相同 commandId、相同 action、相同 input hash 对应的规范 payload。
- Gateway 不从 receipt 表恢复 title/time；需要在安全的短期执行上下文中持有 payload。进程重启后若 payload 已丢失，不能从日志/Event 恢复，也不能无输入重放。
- Android 收到重复 commandId 时不得再次调用 `ReminderDraftHandler.create`。
- 如果 commandId 已完成，Android 返回原来的最小 receipt。
- 如果同一 commandId 携带不同 payload，应返回稳定协议错误并记录安全告警事实，不覆盖旧 receipt。
- 在 Android receipt 持久化完成前，禁止自动 Device Command retry。

为验证“相同 payload”而不保存敏感 payload，Android 可以保存规范 payload 的加盐/域分隔 hash；不得保存 title/time 到 receipt index。草稿本体仍只存在于 Companion 的受限草稿存储中。

### 7.3 Acknowledgement

Acknowledgement 必须包含并校验：

- commandId。
- success/error 的严格互斥形状。
- 成功时 `{draftId,status:"created"}`。
- 失败时稳定 errorCode，不含原始异常。

Android 应采用原子顺序：

```text
receive command
    -> validate command/payload
    -> reserve commandId
    -> create or locate one draft
    -> persist commandId -> draft receipt
    -> acknowledge same receipt
```

如果草稿创建与 receipt 持久化不能放在同一本地事务中，就不能宣称跨崩溃 exactly-once；实现设计必须明确崩溃窗口和恢复策略。

### 7.4 结果查询

推荐后续协议提供受限的 command receipt 查询或重复 command replay 行为，但不新增通用 Device query/action：

- 查询键只能是已授权 execution 的 commandId。
- 只返回 `unknown|in_progress|completed|terminal_failed` 和最小 receipt。
- 不返回 title、time、草稿正文或设备内部存储信息。

是否新增专用 receipt query action 必须在实现前单独确认；本设计不授权新增 Device action。

## 8. Audit / Event 行为

保留现有：

```text
tool.requested
tool.approved
tool.completed
tool.failed
```

但在实现阶段需要明确幂等写入：重复读取 completed receipt 不得再次写 `tool.completed`。建议由 execution 状态首次转换时写一次对应 Audit Event，并使用稳定 dedupe key；具体 Event schema 变更需单独审查。

`outcome_unknown` 不得错误记录为 `tool.completed`。是否记录新的最小事件（例如 `tool.execution_outcome_unknown`）需要先经过 Event 定义审批；在此之前可只保留 execution receipt 状态，不临时创造 Event 类型。

Audit/Event 仍不得保存 approvalId、commandId、draftId 或敏感 payload，除非未来单独证明某个 opaque correlation ID 的公共必要性并更新白名单。专用 receipt 表承担内部关联。

## 9. 安全约束

- 不自动执行 Reminder Draft；首次 execution 必须来自匹配的 approved Approval。
- 不因 retry、reconciliation、多实例或重启绕过 Approval。
- 不把一个 Approval 用于不同 Tool、输入或设备。
- outcome unknown 时不自动创建新的 logical command。
- 不修改或接入真实 Android Reminder API。
- 不接入 Calendar、Alarm、Notification、Accessibility、Intent 或后台 Service。
- 不新增 Android Manifest 权限。
- 不新增通用 Device command、任意 action、任意 payload 或远程代码执行能力。
- 不调用模型，不写 Memory，不修改 State 或关系等级。
- 不将模型输出直接用于 Approval 或执行状态转换。
- 所有重要 Audit/Event 事实继续通过 EventStore。
- 日志不记录 token、payload、title/time、response、prompt、聊天、Memory 或 stack。

## 10. 实现前测试计划

所有测试使用 fake adapter、fake transport、临时数据库和 fake Android handler；禁止真实模型、Bark、外部服务或 Android 系统 API。

### 10.1 Migration 与 Store

1. 新数据库初始化包含 Approval/execution receipt schema。
2. 旧版本数据库升级保留现有数据。
3. 重复 migration 幂等。
4. `UNIQUE(approval_id)` 阻止两个 execution。
5. `UNIQUE(command_id)` 阻止 command identity 冲突。
6. 状态约束拒绝非法 transition。
7. receipt 表不含 title/time/payload/response/session/token 字段。

### 10.2 Approval 与原子 claim

1. pending、rejected、expired、Tool/input hash 不匹配均不能 claim。
2. approved 且未过期只能 claim 一次。
3. 两个 Gateway 实例并发执行同一 Approval，只有一个 Provider 调用。
4. 进程重启后重复请求读取既有 execution，不再次调用 Provider。
5. completed 重复请求回放相同 draft receipt，且不重复写 Audit Event。
6. Approval 过期后仍允许确认已 dispatch execution 的结果，但不允许新 execution。

### 10.3 失败与重试矩阵

1. dispatch 前 offline/authorization failure 按策略进入 retryable 或 terminal 状态。
2. retryable execution 只在 Approval 有效时恢复，且复用 executionId/commandId。
3. dispatch 后 timeout 进入 `outcome_unknown`，不进入普通 retryable failed。
4. unknown 状态的重复 execute 不生成第二个 command。
5. 明确协议拒绝进入 terminal failed，必须新 Approval 才能产生新 execution。
6. 每种 transition 在崩溃点重启后均能恢复到安全状态。

### 10.4 Device Command 与 Android

1. 同一 commandId 并发到达两次只创建一个 draft。
2. 同一 commandId 顺序重放返回同一 draftId/status。
3. App 重启后重放仍返回同一 receipt。
4. 同一 commandId 不同 payload/hash 被拒绝且不创建第二个 draft。
5. acknowledgement commandId 不匹配被拒绝。
6. response 丢失后 receipt 查询/重放确认原 draft，不创建新 draft。
7. Android receipt index 不保存 title/time；草稿内容不进入 Gateway。
8. handler 不调用 Reminder、Calendar、Alarm 或 Notification API，Manifest 仍只有 INTERNET。

### 10.5 Audit 与敏感数据

1. `tool.requested/approved/completed/failed` 每个逻辑 transition 最多写一次。
2. completed receipt 回放不产生第二个 completed Event。
3. timeout/unknown 不记录 completed。
4. Event、execution row、command row和日志均不包含 title/time/payload/response/token/session/stack。
5. 业务模块不直接写 events 表。

### 10.6 回归验证

1. 现有 automatic 和其他 user_confirm Tool 行为保持兼容。
2. Device status read-only Tool 不被 Reminder 专用幂等语义扩权。
3. Reminder Draft 第一阶段的 schema、Approval、Authorization 和结果白名单保持不变。
4. `npm test` 全量通过。
5. Android JVM 单元测试与 `assembleDebug` 通过（构建环境可用时）。
6. `git diff --check` 通过。

## 11. 实现前决策与结论

跨重启、多实例和网络不确定场景下的 Reminder Draft 幂等不能由当前进程内 `usedApprovalIds`、DeviceCommandStore 或现有 Audit/Event 单独解决。

推荐方案需要：

1. 持久化 Approval。
2. 带 `UNIQUE(approval_id)` 的专用 execution receipt 表和原子 claim。
3. 每个 execution 稳定且持久化的 commandId。
4. Android 侧持久化 command receipt，并对重复 command 回放同一 draftId。
5. 将 dispatch 后 timeout 表达为 `outcome_unknown`，而不是可随意重试的 failed。

这些内容需要 Gateway migration、Android 本地持久化和协议行为变化，因此当前候选仍为 `NOT_READY`。进入实现前必须明确批准 migration、新表 schema、Android receipt 存储、结果查询/重放协议以及失败重试矩阵。本设计不修改现有 Approval 生命周期、不新增 Device action，也不接入任何真实 Reminder 系统 API。
